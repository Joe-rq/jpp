### 4. 没有 `Set` / `Map` 值字面量与类型，`∪` 也用不了

**依据**：`12-IR与类契约-v0.1.md:189`（§2.7）原文"纯函数、数据结构（**列表、映射、集合、记录、
优先队列**）、`loop(bound, variant)`"，把映射、集合和列表、记录、优先队列并列，列为宿主该有的
数据结构。`12-IR与类契约-v0.1.md:323`（§5 骨架表）"搜索"这项技能点名需要"已访集合、不可逆闸门"。
`12-IR与类契约-v0.1.md:416`（§6 Python 构建器示例代码本身）直接写
`seen = set()  # 已访集合：宿主 set`——规范自己的示例代码就在用宿主原生 set。`00-宪法.md:30`
的借用登记表把 `Set ∪ unsure 流是类型错` 列为检查项 E11，前提是 `Set` 得先是一个类型检查器认
得出的类型，不能只是一个记不住字段的泛型名字。

**现在为什么写不出来**：词法层，`crates/jpp-frontend/src/lexer.rs:106` 的符号表只有
`"(){}[],:;.+-*/%!=<>"` 这些 ASCII 字符，加上 `lexer.rs:100` 那七个双字符组合（`-> == != <= >= &&
||`），`∪` 不在其中——遇到它会走到 `lexer.rs:109-117` 的 "unexpected character" 分支直接报错，是
词法阶段就拒绝，不是被忽略或当成别的运算符。语法层，`crates/jpp-frontend/src/parser.rs:381-434`
（`prefix()` 里处理 `[` 和 `{` 的两段）只认列表字面量 `[...]` 和记录字面量 `{k: v, ...}`，没有第
三种容器字面量的入口。类型层，`Set<T>` 这样的写法今天能用现成的 `Applied` 语法解析通过
（`parser.rs:108-117`），但那只是把字符串 `"Set"` 记成一个泛型名字，不代表运行时真的有这个类型。
复核重跑了 `grep -rn "Set<\|Map<\|∪" crates/jpp-frontend/src crates/jpp-frontend/tests examples
lib`：唯二命中是 `crates/jpp-frontend/src/loader.rs:65-66` 的 `HashSet<PathBuf>`/`HashMap<String,
PathBuf>`——那是前端自己内部做导入去重用的 Rust 类型，不是 `.jpp` 用户可见的语法，不构成反例。

**不做的后果**：想写"已访集合"这类需要去重、按成员判断存在的场景，现在只能拿 `List` 配
`contains`（`interp.rs` 的 `BUILTINS` 表里有 `contains`，是线性扫描）硬凑，`12` §5 点名要用到已
访集合的"搜索"骨架、以及 00-宪法登记的 E11 检查（防止把带 unsure 标签的流和确认过的集合悄悄合
并）都没有地方落地。

**依赖（需要一并说明，不是前端单方面能解决的）**：`crates/jpp-core/src/value.rs:367-387` 的 `Value`
枚举现在也没有 `Set`/`Map` 分支（`Unit`/`Int`/`Float`/`Bool`/`Text`/`List`/`Record`/`Fn`/`Builtin`/
`Mat`/`State`/`Question`/`Reading`/`Exit`/`Duty`/`Fail`/`Stop` 十六个变体，逐个读过，没有第十七
个）——文件里的 `BTreeSet`（`value.rs:5,83,88,93,165,175`）只在内部用于 `derived_from` 这类溯源
记录，不是面向用户的值类型。前端就算把词法、语法
都补上，没有 core 侧对应的运行时值类型，这两半也接不上——这条最终要两边商量着来，不是前端单独
能交的作业。

## 二、自核有出入：查到什么就摆什么，不是判定

以下五条都出自 `14` §七的候选清单。逐条在 `12`/`13` 里搜过对应的关键词，结果要么零命中，要么
只能在 `12` 之前那份规范（`11-语言规范-v1.md`，`12` 开篇即整体重写替换了它）里找到出处。列出来
不是要否决——是把我查到的位置、以及现有代码看起来已经用别的办法绕开它的地方摆出来，交给 Codex
和总控判断，不够的话该谁补一条依据或做一次新裁定。

### 和类型 `T ⊎ unsure` / `T ⊎ fail`

**我搜了什么**：`⊎` 在 `12-IR与类契约-v0.1.md` 全文三处命中，全部是内部操作的类型签名——
`do` 的 `Mat ⊎ Fail`（`12:167`）、`ask` 的 `Exit ⊎ Pending`（`12:181`）、J-12 表格行提到"程序
边界不含 `⊎ Fail` 时必须 `on_fail` 处理"（`12-IR与类契约-v0.1.md:272`）。没有一处是"给某个用户
自定义函数的返回值标注 `T ⊎ unsure`"这种通用写法。

**现存机制看起来已经绕开了它**：J-12 的静态检查（`crates/jpp-core/src/check.rs:1001-1063`）靠
数据流分析——找出哪些绑定来自可能产生 `Fail` 的效应，再看它有没有被原样交出去当结果——不看任
何类型标注。J-05 的 `handle` 分支检查（`check.rs:877-903`）是结构匹配：看第二个参数这个记录字
面量有没有 `unsure:` 键、这个键对应的值是不是一个带参数的函数，同样不看类型。`13` §3（"未决结果
按实际去向传递"，`13-Rust实践反馈设计修订-v0.2.md:26`）是"W-untyped-transfer"这条检查的设计
来源——代码里 `interp.rs:667`（锚点 `13 §3 的两个案例`）等四处注释直接写"13 §3"点名依据——要求
返回类型"提到 Exit"，实现用的是 `Type::mentions("Exit")`：静态面在
`crates/jpp-core/src/check.rs:991`，运行期报文锚点 `W-untyped-transfer:` 目前（HEAD `ad5befa`）在
`crates/jpp-core/src/interp.rs:676`（`mentions("Exit")` 判断本身在同一分支往上几行）——这两个
行号属于本轮复核期间仍在改动的 `interp.rs`，按锚点字符串重定位——这个只要类型
树里任何地方出现 "Exit" 这个名字就满足，报错文案给的修法是 `-> Exit` 或 `-> Record<Exit>`，
后者是现有的 `Applied` 泛型语法，不需要真正的和类型。

**会改变这个答案的**：如果以后真有一处检查逻辑必须知道"这个函数声明的返回类型里，哪部分是正常
值、哪部分是 unsure/fail，两边要分开处理"——而不是像现在这样在运行期看实际值的形状——和类型才
是必要的。我没找到这样的检查点。如果总控或 Codex 知道一处没搜到，这条就该从问题变成确认过的
需求。

### `partition` 三流四流

**我搜了什么**："partition" 在 `12-IR与类契约-v0.1.md` 和 `13-Rust实践反馈设计修订-v0.2.md`
全文零命中（两个文件分别 `grep -n partition` 都是空）。唯一的出处是 `00-宪法.md:30`（借用登记
表"SQL 三值 WHERE"一行："`partition` 显式三流/四流；`Set ∪ unsure 流` 是类型错（E11）"）和
`11-语言规范-v1.md` §6.4 一带而过的 "filter（partition）" 组合子提法（旧稿，已被 `12` 替换）。

**现存机制看起来已经绕开了它**：`12-IR与类契约-v0.1.md:323`（§5 骨架表）把"筛"（filter/partition
的中文对应）明确列成"普通函数"，同一行"为什么"写着"全是普通函数；去掉任一语言仍完整"。一个返回
`{yes: [...], no: [...], unsure: [...], fail: [...]}` 的 partition 函数，用现有的记录 + 列表字面
量今天就能写——真正会卡住的不是"partition"这三个字，是它想要的类型精度（00-宪法要求 Set 和"带
unsure 标签的流"是两种类型，互相 `∪` 是类型错），这一半已经并进第一节第 4 条了。

**会改变这个答案的**：如果 `partition` 除了"返回三到四个分好类的流"之外还带着 00-宪法没写清楚
的别的语义（比如 `09-研究方法与假设账本.md:200,209,220` 里零上下文读者提的"on 槽逐元素绑定"、
"确定性过滤位置需 where host e"这些细节），那可能还缺别的东西——但那些细节目前只停留在对
`11` 旧稿的批评记录里，没有进 `12`。

### 守卫命令 `g → S` / `choose` / `switch-case`

**我搜了什么**："switch"、"choose"、"守卫命令" 这几个词在 `12` 和 `13` 全文零命中。三个都能在
`11-语言规范-v1.md` 里找到明确出处：守卫命令 `g → S` 是 `11:15` 那句给整门语言下定义的话（"Jv
是一门判断语言：程序由守卫命令 `g → S` 组成"）；`switch` 的文法在 `11:69`；`choose` 的文法在
`11:72`。`12` 把这份规范整个重写了一遍——标题就是"IR 与类契约 v0.1"，不是"语言规范 v2"——§6.0
执行模型换成了逐语句即时执行，§5 明确把原来该由 `choose`/`switch` 承担的角色拆成 `gate`/`pick`/
`threshold` 三个组合子（"三原语 × 槽参数"，`12-IR与类契约-v0.1.md:320`），同样是"普通函数"。

**现存机制看起来已经绕开了它**：现在 `.jpp` 的 `if` / 函数调用 / 记录已经能表达"三值判断决定走
哪条确定路径"这件事本身（判断的值经 `judge` → `cut` → `handle` 拿到一个布尔或走进 unsure 分支，
再用 `if` 分派），只是没有 `gate`/`pick`/`threshold` 这三个组合子的现成实现——它们不在
`crates/jpp-core/src/interp.rs` 的 `BUILTINS` 表（锚点 `pub const BUILTINS`，HEAD `ad5befa` 上在
`:275-279`，`interp.rs` 复核期间仍在改动，按锚点重定位）里，是 core 或库层要做的活，不是前端语法
挡住的。

**会改变这个答案的**：`13:5` 那句"旧稿的『新文法无限期推迟』不再适用"说明"以后不再加新文法"这
条禁令已经解除，但没有说"加回 `11` 的这几个具体构造"。如果总控或 Nature 认为 `gate`/`pick`/
`threshold` 这三个组合子应该有专门的中缀/前缀语法而不是普通函数调用，那是一次新的语法设计决定，
依据不该是"`11` 本来就有"，而该重新写一条像 `12` 里其它条款那样的规则。

### `while improving + patience`

**我搜了什么**："improving"、"patience" 这两个英文词在 `12` 和 `13` 全文零命中；中文"耐心"只
出现一处，见下。

**现存机制看起来已经绕开了它**：`12-IR与类契约-v0.1.md:189`（§2.7）原文："宿主计量严格单调；或
打分出口带耐心（连续 p 轮无提升即停）；或账本键在本循环内重复即停"——这正是"while improving +
patience"要表达的语义，`12` 把它写成 `loop(bound, variant)` 的一个变式，不是独立语法。
`examples/adaptive.jpp:33-36` 已经有一个真实的、能跑通的例子：`loop(10, 初始累加器, fn(s, index)
{ ...; if done(next) { stop(next) } else { next } })`——`stop(next)` 把完整的累加器记录带出循
环，这条路径完全能装下"跟踪目前最好的分数、连续多少轮没提升就退出"这套逻辑，不需要新关键字。

**会改变这个答案的**：如果有人已经尝试用 `loop` + `stop` 写 patience 模式、发现某个具体地方写
不出来或者写得别扭到需要专门语法（比如累加器要塞进太多字段、或者 `it.n` 不够用），那是一条具体
的反例，能推翻"不需要新语法"这个判断——但目前 `examples/`、`lib/` 里没有这样的尝试留下痕迹。

### 金额与时长字面量

**我搜了什么**："金额"、"时长"、"duration"、"美元"在 `12` 全文只有一处不相关的 "$0"（建造顺序

**现存机制看起来已经绕开了它**：`budget.cost` 在 `crates/jpp-core/src/ast.rs:31` 的注释就是

**会改变这个答案的**：如果以后要给某个字段（比如 `ask` 的超时、或者某种按时长计费的效应）引入

现在只是语法糖，不解决任何现在会红的检查。
