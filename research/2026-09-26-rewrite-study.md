# J++ real-project rewrite study

2026-09-26. Data comes from the rewrite records of 84 real open-source projects in a private-workspace internal rewrite corpus (the first version of this report was written before blocked items were unblocked, covering 72 projects; three later batches — v1, v2, v3 — merged in 12 more unblocked rewrites, included in this version; the corpus holds each project's original code and its J++ rewrite, and is not published with this release — the corresponding repositories are all public open-source projects, referenced here by number and repository name). Extracted per project by the script `research/scripts/rewrite_summary.py`, with output at `research/data/2026-09-26-rewrite-study/2026-09-26-rewrite-data.csv`. Every number cited in this report can be traced back to that CSV or to the script's output — nothing here is written from memory. ## One-sentence conclusion

Take a real, unmodified open-source project, rewrite the part of its code that makes judgment decisions in J++, and compare the two side by side field-by-field under the same batch of "readings" (a probability distribution the judge returns for one question — e.g., "this text has an 0.83 probability of being attack traffic"): 72 of 84 projects (85.7%) match field-for-field exactly; 11 are partially consistent (the parts that match were checked field-by-field, and the reasons for the parts that don't are honestly recorded); 1 could not be compared, because of a genuine defect in the original project itself. The J++ version's judgment-core code has a median of only two-fifths of the original's line count (a median ratio of 2.5x — for every 2.5 lines the original writes, J++ writes 1; this figure uses a "fold-normalized" scope, which normalizes lines of varying length to a standard line every 100 characters, so that a habit of writing especially long or especially short lines doesn't skew the comparison). Call counts to the external judgment interface need to be split into two groups: for the 79 projects that don't compare across candidates, the counts are essentially tied (1,112 calls in the original vs. 1,111 in J++, a ratio of 0.999); for the 4 projects that do compare across candidates (Q-04, B5-09, B5-12, B6-07), J++ splits each candidate into its own separate judgment call, for a combined 18 calls versus 174 — 9.7x the original (gap B155/B156). Across all 83 comparable projects combined, that's 1,130 calls versus 1,285, a ratio of 1.14.

Three key numbers:

- **72/84 (85.7%)** of projects match exactly, field-by-field, under the same reading table ("fully equivalent").
- **A median code-volume ratio of 2.5x** (fold-normalized scope, judgment core only, not counting the host-side code shared by both sides).
- **Call counts split into two groups**: the 79 projects that don't compare across candidates have a ratio of 0.999, essentially tied with the original; the 4 that do compare across candidates have a ratio of 9.7, with J++ asking far more questions. The combined ratio of 1.14 is pulled up by the latter group and is not representative of a typical project.

If the host-side code both sides have to write anyway (data parsing, page rendering, command-line argument handling — glue code unrelated to judgment logic that both sides have to write once) is also counted in the numerator and denominator, using a method common in software engineering (the COCOMO II counting scope, detailed below), the ratio drops to **1.44x** (aggregate scope) to **1.66x** (median across projects). This isn't the data getting worse — it's a different, more conservative algorithm, closer to the question of "how much code does the whole project take" — the reasons both scopes are reported are explained below.

## How it was done

### Where the projects came from

This batch of projects was not cherry-picked — it was drawn from a larger sample, classified by structure, taking one representative per class. Specifically: 3,361 GitHub repository records were first collected (3,353 after deduplication), all of them using JEV (the project's internal name for today's judge) for genuine semantic judgment. A script (not a human) clustered these repositories by "purpose" (moderation, triage, filtering, routing, matching, etc.) and "question-type combination" (a combination of the three judgment structures — yes/no, choose-one-of-K, and scored questions), producing 81 clusters, 75 of which genuinely do JEV judgment (the rest are pure SDKs, pure documentation, toy projects, and the like, with no judgment logic involved). One runnable, representative repository was picked from each cluster; representatives that were read in depth by hand are marked with a "difficulty" rating in the internal selection notes.

The benefit of selecting this way: it isn't picking easy-to-rewrite projects to produce a good-looking number — rewriting one representative is meant to stand in for "can J++ write this entire class of project." 28 items in the selection notes were once marked "blocked" for lacking a language capability; as several rounds of design decisions landed, 24 of those have since been unblocked and rewritten (the 12 merged into this version are part of that group), and 4 remain unrewritten (see "Honest boundaries" below). 84 rewrites are complete and accepted as of now.

### How the rewriting and comparison worked

Every project goes through the same seven-step process (an internal note describing the rewrite process, not published with this release); the core idea is "run the original project's code completely unmodified, write J++ separately, feed both sides the same batch of readings, and compare the output":

1. **Circle the judgment core**: which code defines a question, calls the judgment interface, routes by threshold, or combines the results of several questions — this part is "core." Command-line parsing, network requests, logging, retries — code unrelated to judgment logic — do not count as core, but if this code is glue code both sides have to write anyway (e.g. reading a file into structured data), it's recorded separately as "host-shared" — neither side counts it toward the core line count, but the report lists the host line count alongside it (see "Code volume" below for why).
2. **Write a pre-registration**: before writing any code, predict in writing what line-count ratios this rewrite will hit, which fields won't be comparable, and what pitfalls to expect — cases where the pre-registration was written after the implementation are honestly marked in the results as "a prediction written after seeing the results."
3. **Build inputs, run the original project**: use the original project's own test fixtures, or construct new ones, to cover every judgment branch (including both sides of every threshold, and the ambiguous middle ground). Wire a fake client (behaving identically, same name, same signature as the real one) into the original project's "call the judgment interface" line, run the original project's unmodified code, and record every call's question and answer.
4. **Confirm the judgment paths are genuinely reached**: if a branch in the original project can never be reached no matter how the input is constructed, first check whether the input was built wrong; if, after ruling that out, the branch is confirmed to be dead code or to have some other genuine defect, the project is marked "not comparable" rather than forcing a J++ program to be written just to produce a meaningless comparison. 1 of the 84 projects (`onciopescini/botcraft`) falls into this case — see "Defects found" below (in the full report).
5. **Convert the call log into J++ fixtures** (so the J++ runtime can answer the same questions from the recorded log, with no real network request).
6. **Write the J++ program and run it**, feeding it the same fixtures and the same input.
7. **Compare the two sides' output field-by-field, compare call counts, count lines of code** — the first mismatch is printed out; nothing is quietly hidden, and no field is dropped from comparison just to make things line up.

Two disciplines in this process exist specifically to prevent "the reported numbers look good but are secretly comparing like against like": first, partial equivalence is never excluded from the statistics — a project that genuinely cannot be made fully consistent on both sides still counts in the denominator of 84, with the reasons for the mismatch written up clearly, never dropped just because it looks bad; second, the pre-registration has to be submitted before implementation, so it's possible to check after the fact whether "this rewrite happened to pick inputs that were easy to force to match."

## Results

### Equivalence outcomes

| Category | Count | Share |
|---|---|---|
| Fully equivalent (exact field-by-field match) | 72 | 85.7% |
| Partially equivalent (matching parts checked, mismatches recorded with reasons) | 11 | 13.1% |
| Not comparable (a genuine defect in the original project itself) | 1 | 1.2% |

Compared with the first version of this report (72 projects: 63/8/1), of the 12 newly merged projects, 9 are fully equivalent (Q-03, Q-04, Q-06, Q-07, B6-02, B6-07, B5-09, B5-12, B7-02), and 3 are partially equivalent (B7-01, B6-11, Q-05). Two scope notes are worth stating: B5-09 only tested 4 of its 7 branches — the other three are structurally identical and were skipped to keep the scope manageable, not a language limitation; Q-05 only has `duelo()` matching — `torneo()` is, by design, not compared.

None of the mismatches in the 11 partially equivalent projects come from "didn't bother testing" or "made it work well enough" — every one falls into one of four causes:

- **A capability J++ still lacked at the time of the rewrite**: for example, weighted combination of several questions' readings, cross-question comparison, or ranking by expected score — these fall under "doing arithmetic on readings." The design has since been decided (B153, B166, B167), corresponding to build step 15k (ranking) and the first paragraph of 20j-4 (the author writes the combination rule, then declares a judgment line on the combined score); most of the blocked items became fully equivalent once rewritten under the new version. B6-11 remains partially equivalent because ranking nine different dimensions against each other by score (the `dimensions` field) requires cross-fit comparison, which B153 does not currently support — the checker reports J-04, and it's listed as a new gap.
- **A rounding/tie-breaking boundary**: in B7-01, the original project rounds the expected score to three decimal places before sorting; J++'s merge tolerance defaults to 0, so two tickets scoring 1.4999 and 1.5001 tie in the original but are ordered in J++ — the only difference across 8 tickets, and one the pre-registration predicted in advance.
- **A different random-number sequence**: Q-05's `torneo()` uses Python's seeded `random`; J++'s `rand`/`shuffle` use a different algorithm, so the same literal seed does not produce the same sequence of numbers. The pre-registration already asserted this outcome — the appearance order diverges starting from the second comparison — and it is quantified honestly here, with no adjustment to the input to force a match.
- **A genuine algebraic or floating-point coincidence in the original project itself**: for example, `jevcast`'s three threshold gates produce a boundary case — one that a "single-reading comparison" cannot cover — within the probability-normalization error tolerance the original project itself allows. This is not a J++ defect; it's a side effect of the original project's own tolerance for floating-point error, recorded honestly, with no adjustment to a calibration line's value to force a match.

### Code volume: judgment core only, vs. including host-side code

This data supports two scopes, and the report gives both, because this is exactly where software engineering's long-running dispute over evaluating language efficiency lies: count only the DSL (domain-specific language)'s own text, or spread the generator and glue code into the count as well. `research/地基/研究/08-表达力换算与DSL实测倍率.md` collects several industry cases: the GPU-driver language GAL is 9x if you count only the spec text, dropping to 3.5x once the generator is folded in; the distributed-scheduling language Overlog is about 16.6x counting only its own code, about 3.9x once the accompanying Java code is included. The same case, under a different counting algorithm, can differ by 2.5x to over 4x. J++'s data follows exactly this pattern:

- **Judgment core only (excluding host code)**: across the 83 comparable projects (excluding the 1 not comparable), the median fold-normalized ratio is **2.5x** (interquartile range 1.8–3.6x). Summing every project's un-folded raw line count and J++'s un-folded line count, then dividing, gives an aggregate ratio of **2.98x** (this figure uses un-folded raw line counts, because only 16 projects' records kept a per-file fold-normalized count — too small a sample to sum meaningfully, so the fold-normalized scope only reports the per-project median).
- **Including host code (COCOMO II scope)**: counting the glue code both sides have to write into the numerator and denominator (the COCOMO II manual's rule is "input written for a generator counts as source lines; code the generator produces does not" — J++ source counts as "input written for a generator," and parsing/rendering code shared by both sides is added to both under the same rule, using un-folded raw line counts), the median per-project ratio drops to **1.66x**, and the aggregate (total lines divided by total lines) is **1.44x**.

Both numbers are real, and they don't contradict each other — they answer two different questions. "Core only" answers "how strong is J++'s ability to express judgment logic itself"; "including host" answers "how much total code does the whole project save." Across the 83 projects, the judgment core is a median of 65% of the "core + host" total line count — meaning that, typically, host code and core code are roughly comparable in size, and including it noticeably pulls the ratio down. This is exactly why the report insists on reporting both numbers side by side — reporting only one would be misleading.

## Honest boundaries

- **"Exactly the same" holds under the same reading table** — it does not mean the two sides would get identical judgment results on a real run. A real judge can give slightly different readings on different calls; the 24 projects that read the `confidence` field have a theoretical possibility of diverging on a real run (see "Call counts" above, in the full report).
- **Real-run readings inherently jitter** — asking the same question twice is not guaranteed to give exactly the same probability distribution; this is an inherent property of the judge, not a flaw in this comparison method.
- **The code-volume ratio counts only the judgment core**, not the host code shared by both sides; the report also gives the scope that includes host code — the two scopes don't conflict, they answer different questions (see "Code volume" above).
- **For partially equivalent projects, every reason is written down individually** — some are capabilities J++'s current design has explicitly deferred (arithmetic across questions' readings), some are boundary coincidences within the original project's own floating-point or probability-normalization error tolerance; neither kind of reason was manufactured by trimming the rewrite to fit.
- **Coverage is an upper bound, not an exhaustive real-run test.** This round's clustering-and-representative-selection method guarantees "this class of judgment structure can be written in J++" — it does not guarantee that every single line of code in every repository within a class has been verified; an internal note on the project-clustering and representative-selection method (not published with this release) states this itself.
- **Not yet done**: (1) development hours and cognitive load were not measured — only an experimental design was proposed, not carried out; (2) of the 28 items marked "blocked" in the selection notes, 24 have been unblocked and rewritten as build step 15k and the first paragraph of 20j-4 landed (12 of these are the ones merged into this version across the v1/v2/v3 batches; the part where a reading is treated as a continuous value like a bet size or a position, J++ writes as discrete tiers, and this is honestly listed on its own as a known non-equivalence) — 4 items remain unrewritten (B6-12 and others; the script's "blocked queue" statistics can be checked); (3) a further 25 projects have no `rerun.json` (including the 1 not-comparable project, B3-07) — these were first rewritten after the first tier of build steps had already landed, using the new runtime (4ea646a9) from the start, so there was no separate re-run to write; some of these still show "blocked" in the selection-notes status field, which is simply a record that was never synced; (4) the call-count gap for cross-candidate-comparison projects (B155/B156) has not been closed; (5) B5-09 still has 3 untested branches, and Q-05's `torneo()` only implements the core — not the batch size that grows with a winning streak, nor speculative fan-out.
