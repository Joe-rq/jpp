# 组合标准库初版：共同计划与执行的小范围贯通

2026-09-20。本包实施完成，交回“探讨基于 JEV 构建编程语言”原设计节点验收。

现在，一个组合程序的顺序和分支已经能被共同语言计划器理解。同一份子节点决定它怎样执行、怎样显示结构、怎样估算资源。开发者替换其中一段，三处一起改变，不需要再手工维护一份独立流程图。

本次实际运行的程序很小：读取一个判断，肯定时登记一条记录，否定时返回否定，未决时保留原因和来源。这用于检验语言的组合与执行规则。直接写内核和使用组合库的完整版本都已运行；肯定、否定、未决三种输入的结果、来源、判断调用数、层数和实际动作一致。把“登记一条记录”替换为“登记两条记录”后，计划器预计的动作数从 1 变成 2，实际执行也从 1 变成 2，旧程序仍执行 1 次。

## 1. 两处接口问题已修复

### refine：只更新未决项

`Observation.id` 表示请求内容与来源身份，不表示某一次观察的唯一执行身份。同一请求可能曾经得到肯定，也可能在另一次零预算执行中得到未决。

旧实现按请求身份替换所有同名观察，会把已经得到的肯定一起改掉。现在同时检查“身份命中”和“仍然未决”：已知观察保持原对象；同一未决项的多个引用共享一次更新；未被指定的观察保持原对象。仅指定已知项仍报错，提醒调用者该项不需要 refine。

回归检查包含“已知肯定 + 同身份预算未决，再把未决问成否定”：肯定保持肯定，未决变为否定。检查覆盖对象身份及实际调用次数。见 [test_refine_regression.py](tests/test_refine_regression.py)。

当前工作内核要求显式承接 `Unsure`。组合库的观察边界用原生 `match` 采用 `retain` 策略，保存原出口、原因和来源，再把部分结果交给调用者。未决保持为部分结果。

### bind：factory 自己也能调用能力

`bind` 分成三个阶段：执行前段，调用 factory 获得后续组件，执行该组件。factory 允许自己调用 `judge` 等能力。

| 声明位置 | 含义 |
|---|---|
| `effects=...` | 约束 factory 返回的后续组件；不覆盖 factory 已发生的调用 |
| `factory_effects=...` | 声明 factory 自身能力，合入整个组合的能力集合 |
| 普通 factory 未声明 | 记为未知 `*`，不推断为纯函数 |
| factory 本身是 `Component` | 默认采用该组件的能力声明 |
| 显式空声明 | 只是作者契约，不是对任意 Python 代码的纯净证明 |

共同计划器目前将所有 `bind` 视为不透明节点，资源显示为未知符号。即使 factory 声明为空，也不会据此按零成本计划。后续组件仍单独接受能力子集检查。见 [test_bind_contract.py](tests/test_bind_contract.py) 与 [共同内核贯通检查](tests_integration/test_structure.py)。

## 2. 接入共同语言的位置

Claude 维护共同计划器识别端，Codex 维护组合结构挂载端。对齐过程与 Claude 实施记录见 [Claude计划器接入结果.md](Claude计划器接入结果.md)。

| 组合结构 | 实际执行规则 | 共同 `jv.plan` 规则 |
|---|---|---|
| `then(a, b)` | 执行 a，把结果交给 b | 两段资源相加 |
| `branch(p, yes, no)` | 执行谓词，只执行选中分支 | 谓词资源加两支保守上界 |
| `identity` | 返回输入 | 不增加资源 |
| `leaf` | 执行已有宿主函数 | 复用原 AST 分析；看不到的已声明能力记为未知 |
| `bind / product / iterate` | 沿用已有组合库执行 | 本轮保留为 `opaque`，不假装已经展开 |

`then` / `branch` 不再另存执行闭包，直接调用不可变的 `children`。`describe()` 和 `__jv_structure__` 都由这些子节点投影。`replace_at` 重新调用组合构造器，复核类型、重算能力，产生新组件。共同计划器读取 v1 结构协议；可见叶继续走已有 Python AST 分析。

`Component.program()` 最终仍进入原 `@jv.program`，动作、预算、来源与重放继续由原 Runtime 负责。本轮接入的是共同计划器支持的结构表示；没有新增运行时，也没有修改核心 `ir.py`。后续可在这条接口上扩展结构覆盖。

计划器对数字资源取分支最大值；不可比较的符号使用和值作保守上界，并显示 `W-branch-bound`。动态结构、未知能力或无源码的叶显示未知。可见叶的能力声明仍属于作者契约，并非对任意宿主代码的纯度证明。

## 3. 与直接内核程序的完整对照

可执行完整源码：[out/direct_vs_composed.py](out/direct_vs_composed.py)。包含双方共用的输入、结果与动作定义、完整直接控制流、全部组合叶函数、组合表达式以及运行入口；组件定义完整计入对照。

两种写法做的是同一件事：

| 直接内核写法 | 组合标准库写法 |
|---|---|
| 函数中写 `judge → cut → match` | 写成可复用 `judge_flag` 组件 |
| 接着写 `if` 和两个出口 | 用 `branch(is_accepted, record_acceptance, retain_or_reject)` |
| 上述逻辑写在同一个函数体 | 用 `.then(...)` 连接两个组件 |
| 改函数中的接受分支 | 用 `replace_at((1, 1), record_acceptance_twice)` 替换该子节点 |

这个小程序直接写内核完全可以更短。组合库目前提供的价值，是已经写好的判断、分支和动作可以成为带接口的组件，继续嵌入更大程序；重组结构时，共同计划器和执行一起跟着改变。具体问题、业务规则、动作实现与成功条件仍由程序作者提供。本次不主张十倍代码压缩，也不以此小程序证明复杂应用的全部收益。

| 肯定 | accepted，带来源与记录 | 1 | 1 |
| 否定 | rejected，带来源 | 1 | 0 |
