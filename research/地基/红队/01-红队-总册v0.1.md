## A. 致命问题（会建错、建不起来、或建出来不可靠）

### A1. 验题的"缝"只能验句子，不能定工作点（4.4）
**问题。** 三道"该做"、三道"不该做"，取最小/最大算缝，再在缝里定两条线。这六道题是造单元的人自己挑的，天然干净、天然分得开。真实流上的东西不是这样分布的。父会话已有的数据就是证据：矛盾题在真实文档上，干净臂读数散在 0.2–0.6，注入臂 0.76–0.99；六道人挑的验题会得到一条漂亮的缝，但真实错误集中在 0.4–0.6 这一段，缝告诉你的只是"句子没写歪"，告诉不了你两条线该画在哪。悬空引用题更直接：验题能过缝，真实语料全部 ≥0.6，两条线毫无意义。
**推论。** `a_min − gap/4`、`i_max + gap/4` 没有任何推导，只是把中间一半划成上交带。它和此前收敛的"两条线由这一列在真实流上的错误分布定"不是一回事。
**修法。** 把两样东西分开，各有各的数据源：
- **验题（wording gate）**：builder 的 3+3，只回答"这句话被读成了我的意思吗"。缝 ≥0.20 是上岗的必要条件，不产出边界。
- **校准集（operating point）**：单元在 `draft` 状态"只看不动"地跑真实流时攒下的读数，人标其中一个分层样本（尤其 0.3–0.7 段），两条线由这一列的错误率定：高线之上错误率 ≤ε_act，低线之下漏放率 ≤ε_ignore。校准集不够时（<20 条），两条线取保守默认（0.35 / 0.65）并在名册上标"未校准"。
- 30 道以上改用分位数那条规则删掉，从头就用分位数并加小样本保底，避免规则在 30 处跳变。

### A2. 上交单的人答变成验题，会把单元活活停岗（4.4 + 4.9）
**问题。** 被上交的东西，按定义读数落在上交带里。人答之后它成为正式验题；不管答"做"还是"不做"，`a_min` 或 `i_max` 都被拉进上交带，缝立刻变窄。再加上"新验题落在错的一侧就自动停岗"，几张单子之后全体单元停岗。这是设计上的死亡螺旋，不是实现问题。
**修法。** 人答的上交单进 **校准集**（A1），不进 **验题集**。验题集只收 builder 题和人明确标为"典型例子"的题。停岗触发改为：校准集上自动部分的错误率超过契约线，而不是"一道题落在错的一侧"。

### A3. "回到原样"保险按现有定义永远不会触发（4.1 + 4.10）
**问题。** 东西的 id 含 `supersedes` 和 `made_by`。ping 把 A 改成 A'，pong 改回内容等于 A 的 A''，但 A'' 的 `supersedes` 指向 A'，id 与 A 不同。桌面"整体指纹"若按 id 算，永远不重复，A3.3 必失败；若为了过验收改成按正文算，总册没写，实现者会各写各的。
**修法。** 明确定义：回到原样的指纹 = 本分区活着的东西的 `(kind, body)` 多重集合的哈希，不含任何来源字段。

### A4. `Item.id` 缺 `about`，标记会互相碰撞（4.1）
**问题。** id = hash(kind + body + supersedes + made_by + scope)。同一个单元给两样不同的东西挂同一个标记：kind 同、body（标签）同、made_by 同、scope 同、supersedes 都空 → id 相同 → 第二个标记被当作重复丢掉。
**修法。** id 把 `about` 算进去。

### A5. `with_marks` 视野让每个标记都触发全体重看，安静要走 N 拍、花 N² 次读数（4.3 + 4.6）
**问题。** "脏东西"= 有单元还没对这片视野判断过；视野 `with_marks` 含身上的标记；任一单元挂一个标记，视野指纹变，所有用 `with_marks` 的单元全部重看，再挂新标记，再重看。账本救不了它，因为视野内容真的变了。
**修法。** 默认视野 `self`；`with_marks` 只允许声明"看哪几种标记"，且看不到自己挂的；脏的定义分两级：正文变了 → 全体重看；只有标记变了 → 只有声明看那种标记的单元重看。

### A6. 包内花费和拍数没有并入外层预算，递归包的预算是乘法（4.11）
**问题。** 包"在一拍之内"跑完自己的整轮心跳，有自己的预算；外层预算只数外层的拍。递归包每层各有预算 → 总花费 = 各层预算之积。递归终止只靠"深度由预算封顶"，没有明写深度上限。
**修法。** 花费预算（Jev 金额、写手次数）全局唯一，所有层从同一个池子扣；拍数预算按分区各算；递归深度显式上限（默认 4）。包的"一拍"在外层记为一拍，但内部消耗的钱如实计入全局。

### A7. 已知答案集用大模型定做、两模型一致才留，契约必然虚高（7.4）
**问题。** 两个模型都一致的，恰是没有歧义、措辞干净的题；被丢掉的恰是真实流里最多的那类。用这套卷子量出来的 97% 说明不了真实流上的表现，消融表里"关掉 unsure 出口 → 正确率跌破 97%"也可能根本跌不下去，因为卷子太容易。
**修法。** 终卷必须来自真实流：从 draft 模式跑过的真实东西里按读数分层抽样（每段等量，尤其 0.3–0.7），人标（Nature 标 60–100 条，而不是抽查 30 条大模型的产物）。大模型定做的题只允许当练习卷。契约按读数段分别报告。

### A8. 不变式四与契约校门槛的关系没说清，留了后门（4.0 + 7.4）
**问题。** "边界只由验题算出"与"契约实测来校门槛"看起来矛盾。如果契约可以改每个单元的边界，"为了过验收手调边界"就从后门回来了。
**修法。** 写死：契约只能改**全局参数**（缝的门槛、上交带的宽度、ε_act/ε_ignore），永远不能改单个单元的两条线。

### A9. 同层同优先级即上交，试验台 A 的"改不停"实验造不出来（4.8 + 8.1）
**问题。** `shorten` 和 `add_context` 同为效率层优先级 5，两者在同一拍都想取代同一样东西 → 裁决判平局 → 上交。它们永远不会轮流拉扯，A3.4 无法复现，"改不停"保险测不到。
**修法。** 两者给不同优先级，让它们轮流赢；或 A3.4 改用一个自己和自己拉扯的单元（看到 X 就改成 Y，看到 Y 就改成 X）。同时明确：同层同优先级冲突在正常系统里应视为**定义错误**，由静态检查报出，不应靠运行时上交兜底。

### A10. Choice 用 `confidence` 当门槛，父会话数据已证明不可靠（4.4）
**问题。** 父会话实测：有矛盾组 confidence 0.53–1.00，无矛盾组 0.13–0.99，45 对里 19 对重叠。二选一和六选一的 confidence 也不在同一尺度。
**修法。** Choice 的出口按**选中项那一列的概率**定两条线，与 Noul 同一套机制；confidence 只显示不门控。

### A11. E5 无法在第零步做，E7 今晚不该做（7.0）
**问题。** E5 的过关线含"出口不翻转"，出口边界要到第一步才有。E7 只服务第六步。
**修法。** E5 改为只测读数漂移（中位 ≤0.05）并记录相对 0.5 的翻转，在第一步之后补跑出口版本；E7 推迟到第六步。

### A12. 时间估计与"明天能用"冲突，且门禁依赖睡着的人（7、9）
**问题。** 七到十个工作日，每步要 Nature 签字才能开下一步。今晚没人签字。
**修法。** 今晚把"人签字"替换为"独立验收 agent 签字"，人签字明早一次性补做；步骤按 C 节压缩为今晚一轮。

### A13. Python 3.11+ / typesafe_sdk / FastAPI 全部与本机不符（6.1）
**问题。** 本机 Python 3.9.6，没有 SDK。观察窗是一个独立工程。
**修法。** 直接用 HTTP（`run_eval.py` 已验证形状），标准库 `urllib` 或 `requests`；观察窗今晚做成"日志 → JSON → 一个静态 HTML"，无服务端。

### A14. 账本的键可能要包含同批问题（4.7，取决于 E2）
若 E2 不成立，账本键必须含批次组成，"宽度免费"要打折，第二拍零调用也不再成立。E2 因此必须第一个跑。

## E. 结论

总册的骨架是对的，可以按它建。但有三处按字面建会建错：验题的缝被当成了工作点（A1），人答的上交单回灌验题会把单元逐个停岗（A2），"回到原样"保险按现有 id 定义永远不触发（A3）。这三处都是定义问题，各改一段话即可，今晚必须先改再写代码。契约那张卷子（A7）如果用大模型定做，97% 这个数不说明任何事，真实流分层抽样加人标是唯一诚实的做法，明早 Nature 要花半小时标题。

今晚可以交付的核心：桌面、流水账、账本、三种 Jev 眼加代码眼、四只纯代码的手、心跳、四道保险、裁决、上交到人、包和递归，加一个砍掉大模型写手的试验台 A，以及 E1/E2/E4/E6 四个前提实验的数字。推迟的只有大模型写手、规则上桌、第二试验台、静态检查器、观察窗服务端。这些推迟不减损"能用"，减损的是"证明它是地基"，那是明天的事。
