## 1. `probe` / `run` / `export`

不想花新钱，直接看今晚已经真实跑好的一个 run（15 个单元、14 条便条，`probe` 花
$0.0012 + `run` 花 $0.0011，命令行当时打印的数字如此——`probe` 那 17 次调用的
Log 后来被同名的 `run` 覆盖了，`runs/demo-am/log.jsonl` 里现在只剩 `run` 阶段的
17 次，是本系统"同一个 run id 非续跑时会截断旧 Log"的已知行为，不是数字错了）。
共 34 次真实 Jev 调用，`run` 结束状态 `waiting_on_human`，人队列还留着 31 条没答。

**这个 run 已经跑好了，下面这条是唯一现在该跑的**（零花费，只是重新导出
`viewer.json`）：
```
.venv/bin/python -m foundation export demo-am
```
**不要**把 `probe`/`run` 那两条命令原样再跑一遍——`demo-am` 这个 run id 已经在用，
非续跑模式下重跑会截断它的 Log、重新真花一遍钱，还会把第 4 步要用到的那条 unsure
冲掉。想看那两条命令长什么样，往下翻"如果你想自己从头走一遍"。

**如果你想自己从头走一遍**（约 $0.002-0.003，几十秒）：把 run id 换成一个新名字
（比如 `verify-<今天日期>`），`probe` 和 `run` 用**同一个**名字就会自动衔接
（`run` 会自己去读同名 `probe` 存的名册，不用手动传 `--roster`）：

## 3. 看哪些数字

七个标签页，五到十分钟只需要看这四个：

- **单元名册**：每个单元的**缝**（`gap`，越高越有把握，`probe` 的过关线是 0.20，
  安全层 0.30）、**状态**（`on_duty` 能真动手／`draft` 只能挂"would_act"标记不能
  真动手／`suspended` 停岗）、**两条线**（`hi`/`lo`，`calibrated` 字段——今晚校准集
  基本都不到 20 条，这个字段大概率是 `false`，正常）、**花费（估）**——这一列是按
  同一次调用里参与的单元数摊出来的显示层估算，不是账本原始值，脚注写了这句话。
- **账**：调用数、账本命中率（`cache_hit_rate`）、花费——`demo-am` 的 `run` 那一段
  真实数字是 17 次调用、命中率 0（还没有任何重复读数）、$0.00112。
- **上交队列**：还有多少条 `unsure`/`ask` 没人答。`demo-am` 现在还有 31 条。点开
  一条，页面会直接给你一行可以复制粘贴的 `answer` 命令——下一步就用这个。
- **拍线**：想看某一拍具体谁看了什么、读数多少、被裁掉了什么，点开看一眼就行，
  不用逐拍看完。

## 4. 答一张上交单，看线动

**从"上交队列"标签页挑一条**（任意一条都行），复制它给你的命令，粘到终端里跑。
不想自己挑，这里给一条今晚验过的现成例子——`urgency`（correctness/10，今晚
`on_duty`）单元的一条读数 `p=0.75` 的拿不准：

```
.venv/bin/python -m foundation answer demo-am 425cd294338e59e0 act
```

跑完终端会直接打印当前校准集条数和当前两条线，比如：
```
已记下：425cd294338e59e0 → act
校准集 2 条；两条线 hi=0.65 lo=0.35 校准=False
```
条数从 2 起跳，不是从 1——`urgency` 这个单元在写本文档时已经被手动答过一条。如果
你答的是别的单元或别的 run，条数会不一样，看它随你每答一次而增加，比具体是几更
重要。

**如实说一句**：`hi`/`lo` 这两个数字答一次不会立刻挪动。施工单 §3.4 定的规则是
校准集不满 20 条前，两条线锁在默认值上（安全层 `0.75/0.25`，其余 `0.65/0.35`），
实时反映你刚才那一下的只有"校准集条数"和"校准=false"这两处。这不是 bug，是故意
的：不到 20 条就让线跟着挪，等于让一两次人答就能左右系统的判断标准。想亲眼看到线
真的算出新数字，施工单 §8 S4.4 已经用 20 条构造记录真实测过一遍（见
`foundation/reports/stage-4.md`），不需要你今晚再攒 20 条才能确认这条机制成立。

答完要让这个动作真的执行（打上标记/改写正文），续跑一次：
```
.venv/bin/python -m foundation run a_notes --run demo-am --resume
```
然后回到第 1 步的 `export` 命令重新导出，回 viewer 里刷新看桌面多了什么、队列
少了一条。

## 5. 契约抽样清单：看 + 标注

打开 `foundation/reports/contract-sample.md`——74 条真实便条跑 `draft`（一只手
都没动）的读数直方图，每个 jev 单元一段，段下面是按读数分层抽的清单，最后一列
是空的「人标」列。

**标注方法不变**：纯 Markdown 表格，直接在「人标」那一列的单元格里打字，三选一：
`act` / `ignore` / `说不清`（说不清或留空都会被跳过，不进校准集）。不需要命令，
就是手改文本文件、存盘。

**命令**：`contract-import`，总控授权补建（原因记在 `DECISIONS.md`「收尾后补：
contract-import」）——标签写在 Markdown 里存档，如果没有落点进
`calib/<unit>.jsonl`，标注就是白做。标完、存盘之后跑：

```
.venv/bin/python -m foundation contract-import a_notes foundation/reports/contract-sample.md
```

不用给 `--run`——默认就是当初跑 `contract` 时用的那个 run 名（`contract-a_notes`），
校准集会写到 `foundation/runs/contract-a_notes/calib/<unit>.jsonl`，跟 `answer`
命令写的是同一份文件、同样的字段（`view_fp`/`p`/`label`/`source: human`）。跑完
终端会打印每个受影响单元的校准集条数、当前两条线 `hi`/`lo`、`calibrated` 是否为
真、有没有触发停岗。

`view_fp` 不是从表格里读的（表格「正文」那列被截到 60 字，不能拿来重新算哈希）：
工具按「便条」列的文件名去试验台目录里找到原文件，读出未截断的正文，用
`core/view.py` 同一套算法现算一遍——已经拿 `runs/contract-a_notes/log.jsonl` 里
真实的 `reading` 事件核对过，逐字节相同。

**如实说一句**：校准集不到 20 条时，两条线仍然锁在默认值上不动（§3.4），这不是
`contract-import` 没生效，是设计如此——不到 20 条就让线跟着挪，等于一两条标签就能
左右系统的判断标准。想看到线真的挪动，得攒够 20 条（第 4 步已经用构造数据验过这条
机制成立，见 `foundation/reports/stage-4.md` 与 `foundation/tests/test_contract_import.py`）。
