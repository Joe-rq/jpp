## DI-1 S5.2 前半句「交出物 id 集合相同」在 §2.1 的 id 定义下结构性为假

（修复轮 1，2026-09-20 夜。上游：`DECISIONS.md` D2-1 / D2-2（建造者）、
`foundation/reports/stage-5.md` S5.2（独立验收，判 FAIL）、本轮 F2-1。）

### 被取代的判据原文

施工单 §8 S5.2：「tidy_note 单独跑 12 条 fixtures 记录交出物；放进一个外层包
再跑同样输入，**replay 模式交出物 id 集合相同**，record 模式出口序列相同。」
这里只动前半句（id 集合）；后半句由 S5.2b 承接，见下。

### 现象（独立验收的真实数据，不是推演）

`accept-s52-tidy`（`--pack tidy_note`）与 `accept-s52-wrap`（`--pack wrapper`，
跑前从 tidy 复制账本去噪）跑同样 4 条便条，根分区交出物
（`DELIVERABLE_KINDS = note.clean / note.held / unsure / ask`）
**15 件 vs 13 件，交集 0 件，完全不相交**。
（建造者自己那两次 run `b2-*` 记的是 14 件 vs 14 件、写手没碰过的 13 件 vs 13 件，
见 build-2 交付说明 §3.4——两组数字来自不同的 run，不是互相矛盾。）

### 为什么不是实现缺陷

`Item.id = H(kind, body, about, supersedes, made_by, scope)`（§2.1）。
tidy_note 单跑时它的实例分区名是 `/tidy_note/H([根分区原件 id])`；套进 wrapper
之后，它的 inlet 是 wrapper 复制出来的那份（`made_by='pack:wrapper'`、`scope`
也不同，D2-1），复制件 id 天然不同，于是实例分区名本身就不同，下游每一代
（`supersedes` 进 id）全部错开。交上来的那一件 `made_by` 也不同
（`unit:done_checker@1` vs `pack:wrapper`）。这三处都在 id 的定义里，
与 record/replay 无关（id 是纯函数），与 Jev 噪声无关。

往上交时把 `supersedes` 改写成父分区里的对应物救不了——**父分区里没有对应物**，
中间那代是包的私有产物，按 S5.1 就不该出现在父分区。

### 三条不选的路，和不选的理由

1. **把 `scope` 从 id 里拿掉**：两个分区里正文相同的东西会撞成同一个 id，
   S5.1 的隔离当场失效。代价远大于这条判据。（D2-1 已否决，本轮复核同意。）
2. **复制件强行保留原件 id**：与 §2.1 的 id 定义在数学上不能同时成立（D2-1）。
3. **给 Item 加一个不进 id 的血缘字段（trace / origin），改比 trace 集合**
   （本轮新提出，**否决**）：
   - 若 trace 由内容推导，写手一改写它就跟着分叉——分叉位置与 `(kind, body)`
     完全相同，等于把 S5.2c 用更多内核代码重写了一遍，一无所得；
   - 若 trace 纯按结构（派生位置）推导，正文不同也照样相等——**严格弱于**
     现在已经通过的 `(kind, body)` 多重集合判据；
   - 两种都要给 `Item` 加字段，会落进每一条 item 事件里，把已经绿的 S1.4
     （从 Log 重建）、S2.3 / S2.5（逐字节比对）和 `contract-sample.md` 的
     可复现性重新拖回风险区；
   - 并且它仍然不会让施工单那句话变真，只是让**另一句话**变真——和直接改判据
     是同一个动作，炸面大得多。

### 取代它的判据（两条，都已在真实数据上通过）

- **S5.2b 出口一致**：同一个 `(unit, view_fp)` 组合，套壳与不套壳读出同一个
  出口。`view_fp` 只由正文决定、与 scope 无关（`core/view.py::build_view`），
  套一层壳不改变喂给单元的正文。真实数据：45 个重叠 key，0 处不一致。
  （披露：wrapper 那次跑之前复制了 tidy 的账本，重叠的
  `(view_fp, question_fp, model_version)` 命中同一条缓存答案——这条证明的是
  「套壳不改变该配的出口」，不是「两次独立真实调用碰巧一致」。）
- **S5.2c 内容不变**：剔掉被写手碰过的那一代及其全部后代之后，两边根分区交出物的
  `(kind, body)` **多重集合完全相同**（9 件 vs 9 件）。这是「替换不变」这句话
  真正想说的东西：外面换个壳，交出来的内容不变。
  （剔写手是必须的：`clients/writer.py` 的后端 `claude -p --model haiku`
  不是逐位确定的，这是写手的性质，与包无关。）

### 若将来真要满足原文，要付什么代价

要让「交出物 id 集合相同」为真，等于要求 id 对「外面套了几层壳」不敏感，
即从 id 里去掉 `scope`、`made_by`、`supersedes` 三者中至少 `scope` 与 `made_by`。
那时必须另建一套分区隔离机制（不靠 id 天然不撞），并重写 S5.1 的判据与
`Table.alive` 的分区语义。这是 §2.1 与 §3.9 的一次正面重构，不是修一个 bug，
应当在总册层面决定，不在今晚的地基里做。

### 范围披露

施工单 S5.2 原文写的是 12 条 fixtures；独立验收与本轮复跑用的是骨干子集
`SUBSET_NAMES` 的 **4 条**（`01_promise` / `02_blame` / `03_privacy` /
`10_clean`）。不相交这件事是结构性的、与条数无关（每一条便条的每一代 id 都错开），
但上面那几个件数是 4 条输入下的数，不是 12 条下的数——本轮没有按 12 条重跑，
理由是多跑 8 条不改变结论，只增加真实花费与写手非确定性。

### 范围披露的后续（修复轮 2，2026-09-20 08:xx，`DECISIONS.md` F2-2）

**作废的是上面那条「范围披露」，不是 DI-1。DI-1 整体依旧有效。**

上面那条「没按 12 条重跑，理由是不改变结论」的披露，本轮补测掉了。
`test_s5.py` 新增 S5.2e/f/g 三条测试与一对新 run
（`runs/accept-s52-full-tidy` / `accept-s52-full-wrap`），把同样三条判据放在
**全部 14 条便条**上重跑（14 是任何 12 条子集的超集；仓库里没有任何地方定义过
「哪 12 条」，挑一个 12 条口径本身就会变成一个可调的旋钮）。4 条那组的**测试代码与
在册数字一个字节没动**，stage-5.md 引用的仍是它们（run 目录本身会被每次复跑重写，
那是验收流程本来的行为）。

这对新 run 实际跑了两次（先单独跑三条新测试，后全量复跑时模块级 fixture 重跑一遍），
两组数字都如实记下，磁盘现存的是第二组：

| | 第一次 tidy / wrapper | 第二次（现存）tidy / wrapper |
|---|---|---|
| 根分区交出物 | 49 / 46，交集 **0** | 48 / 44，交集 **0** |
| `(unit, view_fp)` 重叠 key | 162 个，**0 处**不一致 | 162 个，**0 处**不一致 |
| 写手没碰过的交出物 | 34 / 34，多重集合**相同** | 34 / 34，多重集合**相同** |

件数浮动来自写手 `claude -p --model haiku` 的非确定性；三条不变量两次都成立，
所以 14 条这个规模上是两次独立确认，不是一次侥幸。过滤规则
（`_writer_output_ids` + `_untouched_alive`）与 4 条那组共用同一段代码，
没有为了过线加宽任何一处。两次真实花费分别 $0.00139 与 $0.001383。

结论没变，变的是它的成色：「不相交与条数无关」从推论变成了测出来的事；
S5.2b / S5.2c 两条取代判据在施工单原文要求的规模上也成立。
按字面，「交出物 id 集合相同」在 14 条上依然为假——DI-1 整体依旧有效。
