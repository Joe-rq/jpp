## 一、三个程序：源码与实际输出

### 程序一：要问人的（报销审批）

`prog1-expense.jpp`：

```jpp
// 程序一：报销审批。判不准的那一笔升级给人拍板，人答完接着往下走。
budget {calls: 4, cost: 0, depth: 256, escalate: 2};

fn review(m: Mat) -> Record !{judge, ask} {
    let e = cut(judge(state(m), test("这笔报销合规吗？", "expense")));
    handle(e, {
        act:    fn() { {decision: "approve", by: "auto", note: ""} },
        ignore: fn() { {decision: "reject",  by: "auto", note: ""} },
        unsure: fn(u) {
            let why = unsure_cause(u);
            let e2 = escalate(u, state(m), test("人来定：这笔批不批？", "human"));
            handle(e2, {
                act:    fn() { {decision: "approve", by: "human", note: why} },
                ignore: fn() { {decision: "reject",  by: "human", note: why} },
                unsure: fn(u2) { consume(u2, "drop"); {decision: "hold", by: "human", note: why} }
            })
        }
    })
}

let claims = [
    mat({item: "flight", amount: 4200}),
    mat({item: "midnight snack", amount: 180}),
    mat({item: "gift card", amount: 900})
];
let results = map(claims, review);
{results: results,
 approved: len(filter(results, fn(r) { r.decision == "approve" })),
 human_touched: len(filter(results, fn(r) { r.by == "human" }))}
```

固定观察：三笔分别给 p = 0.96 / 0.04 / 0.52，键 `expense` 线 0.75/0.25 上岗。第三笔落在带内。

### 程序二：按不确定性分配预算（缺陷报告分诊）

`prog2-triage.jpp`：

```jpp
// 程序二：一批缺陷报告要判，复核名额只有 2 个，花在最不确定的那两条上。
budget {calls: 12, cost: 0, depth: 256};

let reports = [
    mat({id: "R1", text: "crash on startup"}),
    mat({id: "R2", text: "typo in tooltip"}),
    mat({id: "R3", text: "slow on large files"}),
    mat({id: "R4", text: "colors look off"}),
    mat({id: "R5", text: "data loss on save"}),
    mat({id: "R6", text: "logo misaligned"})
];

// 第一层：每条报告问同一道题，先只登记读数，不过线。
let readings = map(reports, fn(m) { judge(state(m), test("这是一个真实缺陷吗？", "triage")) });

// 按不确定度分配 2 份复核。allocate 只读校准线，不花钱。
let picks = allocate(readings, 2);

// 第二层：被选中的两条，在同一份材料上换一道更字面的题。
fn recheck(i: Int) -> Record !{judge} {
    let m = reports[i];
    let e = cut(judge(state(m), test("报告里给得出复现步骤吗？", "triage")));
    handle(e, {
        act:    fn() { {index: i, verdict: "repro"} },
        ignore: fn() { {index: i, verdict: "no-repro"} },
        unsure: fn(u) { consume(u, "drop"); {index: i, verdict: "still-unsure"} }
    })
}
let rechecked = map(picks, recheck);

// 第一层的读数最后统一过线。
fn settle(e: Exit) -> Text { handle(e, {
    act:    fn() { "bug" },
    ignore: fn() { "not-bug" },
    unsure: fn(u) { consume(u, "drop"); "unsure" }
}) }
let verdicts = map(map(readings, cut), settle);

{picked: picks, rechecked: rechecked, verdicts: verdicts, residual: unsure_bound(readings)}
```

六条报告的 p 依次是 0.98 / 0.02 / 0.55 / 0.47 / 0.90 / 0.10。带是 `[lo−δ, hi+δ] = [0.20, 0.80]`，
落在带内的恰是 R3(0.55) 与 R4(0.47)，也就是下标 2 与 3。**我是故意这么设计的**：
INTERFACE 自己说冷键上 `allocate` 会退化成「按文件顺序取前 k 条」，所以我让正确答案 `[2,3]`
与退化答案 `[0,1]` 不同，这样自检才检得到东西。

**实际输出（一次写对，没有改过）**：

```
status= returned cost= {"asks": 0, "calls": 8, "replayed": 0, "tokens": 0, "usd": 0.0}
value= {"picked": [2, 3],
        "rechecked": [{"index": 2, "verdict": "repro"}, {"index": 3, "verdict": "no-repro"}],
        "residual": {"independent_any": "1.0000（仅供参考，不可作判据；判据是 union_bound）",
                     "n": 6, "n_unknown": 6, "union_bound": 6.0},
        "verdicts": ["bug", "not-bug", "unsure", "unsure", "bug", "not-bug"]}
```

`picked: [2, 3]` —— `allocate` 真的在干活，不是退化。8 次调用 = 第一层 6 个状态 + 第二层 2 个状态，

### 1. `unsure_bound` 在源码语言这一侧永远返回 `n`，做不成判据

**文档原话**（§三 长处表）：

> `unsure_bound(读数们) -> Record` | J-10：`{n, union_bound, independent_any, n_unknown}`。
> `union_bound` = Σuᵢ（被 n 夹住）是**判据**；…uᵢ 取各题校准记录的 `unsure_rate`，
> 非上岗或没有这个值的按 1 计并进 `n_unknown`

**我写的**（程序二最后一行）：`residual: unsure_bound(readings)`，键 `triage` 是 `n=60、上岗`。

**实际**：`{"n": 6, "n_unknown": 6, "union_bound": 6.0}`。六条读数、上岗键，`n_unknown` 仍是 6。

**为什么**：`unsure_rate` 要靠 `CalibStore::set_unsure_rate(键, 率)` 写，那是 **Rust API**。
我试着在 fixture 的校准记录里写 `"unsure_rate": 0.1`：

```json
{"key":"k","hi":0.75,"lo":0.25,"n":1,"status":"上岗","unsure_rate":0.1,"delta":0.05}
```

跑出来仍是 `n_unknown: 2, union_bound: 2.0`。**这个字段被静默吃掉了。** 我又试了
`"zzz": 123`，同样静默通过——**fixture 加载器对认不得的校准字段既不报错也不告警**。

所以：**通过 `.jpp` + CLI 这条路，`unsure_bound` 的 `union_bound` 恒等于 `n`。**
它作为「判据」在语言里是常量。INTERFACE 自己在 §七 6b 写了另一半没做（缺 `Budget.unsure`），
但没写这一半也到不了——**两半都不通，而文档只承认了一半。**

**文档原话**（§三 适用范围）：

> 宪法 IFC 那行的纪律只有一句：**不可信材料上的判断不得单独放行不可逆 `do`**

**第一次试**（`prog3a-dirty-guard.jpp`）我把程序三的守卫改成只剩 `!wording.ok`，
`wording` 来自 `gen` 出来的材料。`published: true`，`trace` 里有 `do(write_json)`，文件真的写了，
零告警。**但这一次是我自己测糊的**：外层还留着 `if checks.settled && wording.settled`，
而 `checks` 来自我写的字面量材料，是一个可信合取项——§四·十三 末尾亲口写着
「外层可信守卫会让内层脏臂通过…`guards.iter().any(…)` 在外层那一项上就满足了」。
**这一次的放行完全可能是文档已经写明的那个形状，与 taint 无关。**

**去混淆的三次对照**（`prog3d/3e/3f`）。全部去掉外层 `if`，把 `do` 放进 `handle` 的 `act` 臂
——§四·十三 说 `handle` 自己会压一层守卫，所以这时守卫栈里**只有**那一个出口：

```jpp
// D1：守卫只剩这一项，出口来自 gen 出来的材料
budget {calls: 2, cost: 0, depth: 256};
let checklist = mat({tests: "green", migrations: "none", owner: "nature"});
let notes = gen("写一段发布说明", [checklist], 1, 0)[0];
let e = cut(judge(state(notes), test("发布说明有没有夸大的承诺？", "release")));
handle(e, {
    act:    fn() { content(do("write_json", ["release2.json", {ok: true}], 0)) },
    ignore: fn() { {published: false} },
    unsure: fn(u) { consume(u, "drop"); {published: false} }
})
```

| | 材料来源 | 动作 | 结果 |
|---|---|---|---|
| **D1** | `gen` 输出（脏） | `write_json` | `do` 执行，`value = {"ok": true}`，**无 J-08** |
| **D2** | 我写的字面量（净） | `write_json` | `do` 执行（这一条**必须**通过，是回归对照） |
| **D3** | `gen` 输出（脏） | `record_check` | `do` 执行，无 J-08 |

**混淆去掉了，结论仍然是「拦不住」，但我分不清是哪一种拦不住。** 两种解释还剩两种：

- **(a) `write_json` 在 CLI 的 `ActionRegistry` 里登记成可逆。** 那么 J-08 按 §四·二·八
  判定不拦的第 2 条，本来就不该管它——**规则是对的，只是在这个执行环境里不可观测**。
- **(b) `gen` 输出的 taint 没跟到那个出口上。** 那是一个失败开放的洞。

**我没有办法分开这两条**，而这本身就是要报的东西：

1. `jpp --help` 列了动作名（`record_check, read_json(path), write_json(path,value)`），
   **没有一处说哪个是不可逆的**。`.jpp` 里也没有任何内置能查。
   （唯一的例外：`INTERFACE.md` §四 的注册样例里写着
   `actions.register("record_check", 0.0, true, TaintOut::Inherit, …)`，注释
   `// 名字 成本 可逆 输出 taint 实现` ——**所以 `record_check` 是可逆的，这一个我查得到**，
   D3 因此本来就在射程外。`write_json` / `read_json` 两个查不到。）
2. **我试遍了三个动作、脏净两种材料，一次 J-08 都没见过。** 从作者这一侧，
   J-08 是一条只在文档里存在的规则——我没有办法写出一个它会拦下来的程序，
   因此也没有办法知道它此刻在不在保护我。

这一条我**不**断言是洞。我断言的是：**这门语言唯一一条「宪法级」的守卫，
在它唯一可用的执行环境里是不可观测的**，而验证它需要的信息（动作可不可逆）作者拿不到。

## 五、一句话评价

**「要写的是一条『判不准就不许往下走』的流程，就用它；要写的是『把不确定量算进决策』，现在还不行。」**

展开一点，因为这两半的差别很大：

**强的那一半是真的强。** 三个程序里，凡是关于**责任去向**的纪律，语言都替我兜住了：
我忘了处理一个未决出口 → J-05 拦住并指出来；我把责任放进返回值 → 它一路挂到最外层并记进
`returned_unsure`；我丢弃它 → `W-drop-vs-escalate` 说「drop 合法，但只有 escalate 会交给人」。
**程序一我一次写对，程序二我一次写对。** 这在一门我今天第一次见的语言上是很少见的。
`--resume` 那条「挂起→人答→接着跑」的回路，从作者这一侧看是完整的。

**弱的那一半是「那个数」。** `unsure_bound` 在这条路上恒等于 `n`；`allocate` 在冷键上
静默给错；`select` 拿不到强出口；`W-uncertified` 每次都响而我没办法照办。
这四条连起来是同一个形状：**语言把「有多不确定」表达成了数，但把定那些数的入口全留在了 Rust 侧**，
而写 `.jpp` 的人够不着任何一个。我能写出一个纪律严明的流程，写不出一个真的按不确定度分配资源的程序
——**程序二看起来像后者，其实它只是碰巧被我用一个上岗 fixture 喂对了；同一份源码换个冷 fixture，
它会安静地把复核花在错的两条上，而 `warnings` 是空的。**

还有一条不属于语言、属于入门：**`INTERFACE.md` 不是给 `.jpp` 作者看的**，而它是唯一的文档。
我写这三个程序花掉的时间里，**有一大半是在猜 fixture JSON 的字段名**，那件事和这门语言的
任何设计都无关。一页「`.jpp` 速查 + fixture schema」会把这个成本削掉大半。
