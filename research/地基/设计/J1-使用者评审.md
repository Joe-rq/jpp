## 2. 「充分发挥 Jev」在使用者眼里是什么

对写程序的人，充分发挥 Jev 只意味着三件事：**我不用管题型、不用管批次、不用管窗口**；以及**我花的钱和等的时间我看得见**。

| | L1 | L2 | L3 |
|---|---|---|---|
| 不管题型 | 是。源码只有 test/select/measure，`jv plan` 打印下沉 | 是。同上，另有 `pin` 供实验 | 是。同上，`jc lower` 单独一条命令打印下沉理由，最清楚 |
| 不管批次 | 是。for 体内自动合批 | 是。同层同对象自动融合 | **半是**。融合自动，但我要自己写 `layer`，写错了只得 W-mergeable |
| 不管窗口 | 是。超窗隐式裂变，干跑报告 | 是。同上 | 是，且 E-window/W-fission 报得最细 |
| 成本可见 | 只在 `jv plan`；源码看不出平方项 | **最差**：`rule 退化(c) :- commit(c), …` 一行就是全量跑基准，作者自己承认 | **最好**：`budget layers/cost/time` 写在程序头，编译期核对；D23 直接被判域外 |
| 状态怎么拼 | 我手写 `state(obj, evidence, ctx, ref)` 或 `m with ctx` | **最好**：`judge … on … ctx … over … anchors` 声明槽位，编译器拼 | 我手写 `state(obj:, cands:, ctx:, ref:)` |

结论：L2 在「不用想」上最彻底，代价是「看不见」；L3 在「看得见」上最彻底，代价是「要多写」；L1 居中，但把「拼状态」和「接 unsure」两件事都留给了我，而这两件恰是最容易写错的。

## 5. 收敛建议

**以 L1 为骨，嫁接 L2 的声明与 L3 的可见。** 理由：使用者最终要写的是控制流，命令式是三套里唯一在交互类（D41）和生成类（D7、#77）都能一眼读懂的；L2 的规则在这两类上要靠运行时绑定，L3 在这两类上退化成带寄存器的脚本。

嫁接三处，删两处：
1. **题声明用 L2 的形式**：`judge 名 : test|select|measure = "题面" on … ctx … over … anchors …`。状态由声明构造，程序里不再出现手写 `state(…)`；L1 的 `if 题 on 表达式` 改为 `if 题(实参)`。这一处消掉 L1 最大的写错源。
2. **unsure 接法用 L3 的一行式**：`unsure -> escalate | refine e | drop | continue`，未接是编译错；保留 L1 的块式作为需要多行处理时的形式。#42/#49 的 switch 由此从 15 行降到 8 行左右。
3. **成本用 L3 的 `budget`**：程序头可写 `budget layers/cost/time`，编译期核对，超出报错；域外（D23）由编译器判。`plan/lower` 两条命令照 L3 的分法。
4. **删 L1 的「变式必须是打分题」**：采用 L3 的 `variant host 表达式 decreasing|increasing`，打分变式保留为可选。这一处消掉四条探针里的无增益判断。
5. **不采 L3 的显式 `layer`，不采 L2 的 `iterate`**：层由编译器算，程序员只在干跑里看；迭代用 L1 的 while/ring。

按这套嫁接重写 #42，估计从 L1 的 15 行到 7 行，且 unsure、状态、成本三件最易错的事全部由编译器接管；D41 保持 L1 的 10 行不变。这就是使用者要的：**写的是控制流，题型、批次、窗口、状态拼装、unsure 去向、费用核对六件事一件不用管，且六件都在干跑里看得见。**

## 6. 补：三套对 `10-组合代数-v0.md` 三张表的覆盖（协调者追加）

### 6.2 环节二：七种题式 + 七种选法

| 题式 | L1 | L2 | L3 |

七种选法（候选/材料/标签/读法/动作/问题/假设）：三套都能**用同一个 select 写出七种**，但没有一套把「读法（消歧）」和「假设（解释）」做成可辨识的形式；对使用者来说，它们和「比较」长得一样，题库无法按题式校准或复用。写题四规则：三套都由类型系统守「一题一对象」「量必有锚」「候选集带都不是」；「一跳字面」三套都只能靠题库审核，无编译器检查。

### 6.3 环节三：并 7 / 接 16 / 聚

**并（同状态多题）**：三套都靠编译器融合，程序员只写多道题——7 种全部可写。但第 4 行「选 + 量不一致 → ?」的**一致性检验**三套都没有：写了 select 和 measure 之后，两者矛盾时没有语法让它自动变 ?，要我自己比较出口。这是三套共同的缺格。

**接（输出 × 目标槽 16 格）**——这是差距最大的一张表：

| 格 | L1 | L2 | L3 |
|---|---|---|---|
| 位→材料（门） | if | 规则体合取 | `.act ->` |
| 位→问题（门：问/不问） | 嵌套 if | 规则体先后 | 后层 state |
| 位→候选集（剔除） | 手写集合减法 | `not 不可行(c)` 合取 | 手写 `\` |
| 位→动作（执行/不执行） | `if … { do … }` | `fn!` 在规则体 | `.act -> S` |
| 位→循环（继续/停） | while 只吃量；位要靠 bound 或 refine | iterate 的 variant 只吃聚合 | ring `until` 吃宿主，**位不能直接当 until** |
| 索引→材料（取） | `select … as x` | `x = 选(…)` | `.pick` |
| 索引→问题（路由） | **无**：选中的题不能作为下一道题的名字 | **无** | **无** |
| 索引→候选集（分支） | switch case 内手写 | 规则分支 | `.by_label` |
| 索引→刻度（换刻度） | **无** | **无** | **无** |
| 索引→动作（分派） | `select … { do act(a) }` | `act!(下一步(…))` | `S.execute(nxt.pick)` |
| 档→材料（阈 / 前 k） | `rank` + 宿主 top | `order by` + `top k` | `Ranked` + 宿主 |
| 档→问题（按档换题） | 手写 switch on 档？无此语法 | 规则体 `s = 严重(d), s = 高, 细题(d)` 可凑 | 手写 |
| 档→候选集（保留 ≥ℓ） | 宿主 | `CMP` 合法 | 宿主 |
| 档→刻度（缩放） | **无** | **无** | **无** |
| 档→动作（分配：花多少判断） | **无** | **无** | **无** |
| 档→循环（变式） | while 变式 | iterate variant | ring variant measure |

统计可直接写出的格：L1 约 9/16，L2 约 10/16，L3 约 9/16。三套**共同缺**四格：索引→问题（路由）、索引→刻度、档→刻度（缩放）、档→动作（分配）。这四格恰是「二阶」与「把判断力花在哪」的格子——正是 Nature 说的三种题组合才有意思的地方。另外 ? 的六种固定去向：L1 只有 escalate/refine/continue 三种，L3 有 escalate/drop/merge/后层 四种，L2 有 escalate/keep/drop/refine 四种；「候选集格 → 再生成」「刻度格 → 加锚」没有一套做成固定去向。

**聚**：位的存在/全部/计数区间三套都有；索引的众数（L1/L3 在 select 置换里内置，L2 无显式）、标签直方图（L3 `by_label`，L2 规则派生，L1 手写）；档的分布/中位/前 k（L1 rank、L2 order by、L3 Ranked，中位档都没有）；**混合聚合（高档里的 act 计数）三套都要宿主手写**。

### 6.4 对收敛的修正

第 5 节的收敛建议保持，追加一条：**接表的 16 格应作为语言的固定组合子集**（10 §5 的要求），而不是让使用者用 if/规则/接线各自凑。具体是把「路由、换刻度、缩放、分配」四个缺格和「? 六种固定去向」补成关键字或库组合子；「选 + 量不一致 → ?」做成融合时的默认行为。L2 的声明式题声明最适合承载七种题式（题式可作 `judge` 的第一个词），L1 的控制流最适合承载 16 格（每格一个语句形），L3 的 `.出口 -> 目标` 接线最适合表达 ? 的固定去向。三套各占一张表，这大概不是巧合。
