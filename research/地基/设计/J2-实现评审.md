## 1. 文法与语义是否完整到能写解析器与解释器

结论先行：三套都能写解析器（文法都给了），**没有一套能不补语义就写解释器**。缺口按严重程度列，
「矛盾」指文档自己前后不一致，「未定义」指解释器到那一步不知道该做什么。

### L1 守卫命令式

| # | 类型 | 位置 | 问题 |
|---|---|---|---|
| L1-1 | 未定义 | §4.2 stmt | 文法只有 `let`，没有赋值语句；但 15 条程序里到处是 `归因 = 归因 + {…}`、`错 = 错 − {e}`。赋值不在文法里。 |
| L1-2 | 未定义 · 严重 | §4.4 [for] | `for` 体「无顺序、独立求值、并发」，同时体内对共享集合做 `+`/`−`，还在迭代 `错` 的过程中改 `错`（7.1）。并发下对同一集合的读改写没有定义；迭代中修改被迭代集合没有定义。解释器必须选：要么 `for` 体只允许对累加器做可交换操作（并集、差集）并在迭代结束后一次性合并，要么 `for` 是顺序的。文档两者都没说。 |
| L1-3 | 矛盾 | §4.4 [do] 与 7.3 | 规则：「do 按数据依赖定序，定不了序报错」。7.3 在 `for` 里跑 n 次 `do run(...)`，彼此无数据依赖，按规则应报错；程序却依赖它们并发执行。要么允许「无依赖的 do 并发且结果按程序点归位」，要么 7.3 不合法。 |
| L1-4 | 未定义 | §4.4 [refine] | 「细拆后重入当前守卫」：在 `for` 体内 `refine e`，细拆出的片段是加入当前迭代集合、还是当场递归判？递归判的出口写回哪个变量？7.1、7.6、7.8 三处用法各不相同（7.6 还先往 `出` 里塞了一条再 refine）。 |
| L1-5 | 未定义 · 严重 | §4.4 [escalate]、§4.5 | 「程序在此挂起或返回 unsure（由调用者决定）」。程序调程序时，被调程序的 unsure 到了调用方是什么类型、进哪个守卫的哪一支，没有规则。组合语义在 unsure 这一点上是空的，而 unsure 恰是这门语言的核心。 |
| L1-6 | 未定义 | §4.4 [下沉] | `select` 长候选下沉为 K 道 noul 取最高：全部 ignore 时出什么？最高两者在 δ 内时出什么？（L3 定义了：无 act 或并列 → unsure；L1 没写。）K > 16 段落级怎么办也没写。 |
| L1-7 | 小 | 7.5 | `if 回归 on …` 的 `回归` 未声明；`only`、`middle`、`before/after`、`commits`、`bench_of` 都是未登记的宿主函数。 |

### L2 声明式目标

| # | 类型 | 位置 | 问题 |
|---|---|---|---|
| L2-1 | 矛盾 · 严重 | §4.4 分层 与 D7/E77 | 规则说「`not` 与聚合要求分层，不得递归穿过」。D7 的 `rule 候选(i) :- i in write!(4, spec, top 1(候选(i) by 失败少))` 在自己的定义里对自己做 `top 1` 聚合，正是递归穿过聚合。E77 同构。要让它成立必须引入「上一轮的候选」（时序 Datalog 的 prev 标注），文档没有这个构造，D41 用了一个未在文法里的 `prev_scene` 来凑。 |
| L2-2 | 未定义 · 严重 | §4.4 `fn!` | 「同键至多执行一次」，但 `fn!` 的键是什么没定义：是参数哈希？是（动作，序号）？若是参数哈希，`gen!(8, spec, x)` 在 `x` 不变的两轮里返回同一批候选（不重新生成），iterate 靠键重复停机——这可能是想要的，也可能不是，但必须写明。 |
| L2-3 | 未定义 | §4.4 iterate | `variant max(接近(c) by 接近) increasing`：全部 unsure 时变式是什么？「不严格单调则停」在档位只有 3 档、δ 0.15 的条件下，平台期一轮就停，等于 bound 名存实亡；要定义「不下降」还是「严格上升」。 |
| L2-4 | 未定义 | §4.2 文法 | `bisect(commits(repo), 退化, c)` 把谓词名当参数传，文法的 `expr` 不允许；骨架模板「参数是谓词名」需要高阶规则语法。 |
| L2-5 | 未定义 | §4.4 函数谓词 | `x = 选(…)` 结果 unsure 时「整条体 unsure」；但若这个 unsure 值又被当作 `fn!` 的参数（`act!(下一步(prev_scene))`），`fn!` 收到 unsure 该执行什么？没写。 |
| L2-6 | 矛盾（与实测设计） | §4.4 融合 | 「账本键是（渲染状态，题集）」。E2/E3 已定：账本键排除批次，按（状态，题）。以题集为键意味着同一题同一状态换了一批同伴就不命中账本，要重问，重问有 δ 噪声，重放与新鲜运行的差别被人为放大。 |
| L2-7 | 小 | D7、E45 | `失败少`、`commit(c)`、`baseline_out`、`prod/staging` 未声明。 |

## 2. 下沉、融合、裂变各放在哪一层，规则是否可实现

| | L1 | L2 | L3 |
|---|---|---|---|
| 放在哪 | §4.4 语义规则前三行；作为编译器的一遍 | §4.4 「下沉/融合/裂变」三段；规划器内部 | §2.1 独立的 `jc lower` 遍 + 层的默认行为 |
| 下沉规则 | 段落级 K≤16 → choice；长候选 → K noul；K=2 → noul；档=2 → noul | 平均 ≤300 token 且 K≤16 → choice，否则 K noul；>255 → 裂变再锦标赛；含同伴的 measure → 逐个单独状态只计数 | 表格化：段落级 K≤16 → choice；长候选或 K>4 → K noul；标签集 → choice；档≤3 只要阈值 → noul |
| 融合规则 | 同渲染状态、同层 | 同层、同渲染状态；键含题集（见 L2-6） | 同 state 默认融合 |
| 裂变规则 | 超窗按窗切，对象单独占位，块出口摘要再判 | 按操作分别定义合回：test 用 exists=max，select 每块先选再锦标赛，measure 只计数 | 三种裂变枚举：obj 集合 → 逐元素；cands → 重分组 + 两层锦标赛；ctx → 切块 + 摘要 |

**可实现性。** 三套的三件事都能实现，L2 与 L3 的裂变写得最完整（合回规则按操作分开）；L1 只说「块出口摘要再判」，对 `select` 和 `measure` 的裂变没规则。

**与实测是否一致。** 三套的下沉阈值都在插值。实测只有两个点：E10 段落级候选 K=16 状态 1.8k 一致率 1.00；E9b 代码级 8 候选首位偏置 33%，K noul 14/14 优于 choice 12/14。E10 的代码级 K=4 是 argmax 一致率 0.80、unsure 率 0.50——「代码级 ≤4 用 choice」（L1、L3）没有实测支持，L2 的「≤300 token」是把 E10 的候选长度当阈值，同样是插值。**实现建议**：下沉阈值不写死在编译器里，作为校准存储里的一张**实测表**（题型 × 候选长度档 × K → 一致率、unsure 率），编译器查表；表没有的格子按保守路径（K noul）走并在 `plan` 里标「插值」。这和「线只来自校准」是同一条原则的延伸。

**哪套让规划器最容易做对、最容易做错。**
- **L3 最容易做对**：结构就是计划，规划器只做融合与裂变，不做重排；错只会错在裂变后层数与程序写的不一致，而它已经把这个降为 W-mergeable。
- **L2 最容易做错**：规划器自由度最大（规则图分层、体内字面重排、K、副作用定序）而选择率未知，且 `fn!` 进规则体后「一条规则 = 对全部提交跑基准」的代价在计划里才看得见。它需要一个成本模型加干跑门禁才能安全，这两样都是新写的、没有实测支撑的代码。
- **L1 居中**：控制流显式，层由语句依赖推出，规划器几乎无重排空间；风险集中在 `for` 体的并发语义（L1-2）和融合的边界（同层判定）。

## 3. 确定性与重放：账本键、置换种子、「做」的记录

| | 判的键 | 做的键 | 置换种子 | 反例 |
|---|---|---|---|---|
| L1 | （渲染状态，题，置换种子）— 每题一键，**对** | （动作，序号） | 「从账本来」，新鲜运行未定义 | 7.3 的五个 `do run` 在无顺序的 `for` 里并发，「序号」由完成顺序决定 → 两次新鲜运行的账本键不同，重放对不上。做的键应为（程序点，参数哈希，迭代索引），不是全局序号。 |
| L2 | （渲染状态，**题集**）— 错，见 L2-6 | 未定义（L2-2） | 未提 | 同题同状态换一批同伴 → 键不同 → 重问 → δ 噪声 → 新鲜运行不稳定；`iterate` 每轮全量重求值靠键命中账本才不重问，键含题集则命中率骤降，钱与噪声同时上升。 |
| L3 | （渲染状态，**题集**，置换种子）— 同 L2-6 | （动作，序号）；环内顺序确定 | 「入账」，新鲜运行未定义 | 同一层内多个 `effect world` 的 S 无依赖 → E-order 报错，所以 7.3 式并发只能包成一个 S（`S.rerun(suite, n)`），这是**一致的**；反例在 `effect none` 的抽样重跑核对：宿主函数若读了时钟或环境变量，抽样可能漏掉。 |

三套共同：集合渲染的规范顺序未提（见 §1 末）；`gen`/写手本身非确定，靠账本记录观察是对的，三套都做到了。

只有 L1 的判键是对的粒度。L2、L3 必须改成每题一键，融合只是传输层的打包，不进键——这正是 E2/E3 花钱测出来的结论。

## 4. 与昨晚 `foundation/core/` 的对接

按 `设计/C` §4 的去留表（沿用 7：item/log/table/canon/ledger/eye/registry；改造 11；废弃 3：beat/arbiter/pack）估算新写量。三套共同的改造（outlet 三桥、calib 分题型、probe、params、view → state 四槽、hand → S 注册、guard → 终止条件、escalation、checker 升级）不重复计，只比各自**新写**的部分。

| 新写部件 | L1 | L2 | L3 |
|---|---|---|---|
| 解析器 | 语句文法，中等 | 规则文法 + 高阶参数（L2-4），中等 | 图文法 + 出口连线，中等 |
| 类型检查 | 出口子类型、题类型、unsure 必填、switch 覆盖 | 谓词类型、CMP 合法性、同伴检查（E7）、分层检查 | 线类型、向量化出口类型（L3-1 要先定义）、E-layer、E-unsure |
| 求值/执行 | 语句解释器 + `for` 合批 + 键重复规则；**beat.py 可改造为层执行器** | 分层求值器（半朴素）+ iterate 全量重求值 + supersedes + `fn!` 定序：**一个 Datalog 引擎，最大** | 层执行器（**beat.py 几乎就是它**：一拍 = 一层）+ ring 寄存器 |
| 规划器 | 语句依赖 → 层；融合；裂变；干跑 | 依赖图 → 分层 → **成本模型 + 重排 + 干跑门禁**：最大、最险 | 融合 + 裂变 + 摊平后重算层号；无重排 |
| 骨架 | 用语言写，7 个 program | 规则模板 + 高阶语法 | 6 个 circuit，Tournament 已写出 |

**建造顺序最短：L3 → L1 → L2。** L3 的执行器与 beat.py 同构，规划器最小；L1 多一个语句解释器和 `for` 合批；L2 要新写一个带成本模型的三值 Datalog 引擎，且它的正确性（分层、iterate、`fn!`）没有先行理论，是三套里唯一需要「先证明再写」的。

## 5. 成本可见性

三套的现状：L3 把层写进程序，成本在结构上可读，但摊平与裂变后程序里的层号只是局部真（它自评）；L2 完全藏在规划器里，一条规则可能是平方项（它自评）；**L1 的成本也不可见**——下沉成哪种题、超窗裂成几层、`for` 合批成几次调用，源码上一个字都看不出，只在 `jv plan` 里（它自评弱点 3）。

**实现建议：成本以「声明的预算」进程序、以「报告的计划」出程序，永远不以「程序结构」的形式存在。**
1. `budget layers/cost/time/calls` 作为可选断言（借 L3），编译期与干跑对照，超出即拒绝编译或运行。它只约束，不决定结构，所以摊平与裂变不会让它失真。
2. 编译器输出与源码逐语句对齐的**计划旁注**（`.plan` 侧文件）：每条含判断的语句旁写「层 n · 调用 k · 下沉 choice/K-noul · 裂变 m 块 · 预估 $」。编辑器内联显示，像类型推断的提示。程序员不写层，但看得见层。
3. 运行前的干跑门禁：预估费用超过阈值（默认 $0.10）必须显式 `--confirm`，这条对 L2 尤其是安全带。
4. 下沉决定必须可复核可强制：`plan` 打印理由（K、长度、查表的一致率），`phys:` 提示只在实测表覆盖范围内生效（L3 的 E-K 做法对）。

这样 L3 的核心价值（结构即成本）被保留为报告，L1/L2 不必为它扭曲语法。

## 6. 收敛建议

**以 L1 为骨。** 理由：三套里只有它的判键粒度对（每题一键）；控制流显式使规划器几乎没有做错的空间；交互类任务（做→观察→判→定→做）写起来最自然（L2、L3 都自评这一类最弱）；程序调程序的组合形式与现有 `program` 接口一致；不需要新理论——它的语义缺口（§1 L1-1 到 L1-6）全是「没写」，不是「不知道怎么写」。

**从 L3 嫁接：**
- `state(obj, cands, ctx, ref)` 四槽命名与 `fan(S, K)` 的向量化，加上**向量化出口类型规则**（obj 是集合 ⟹ 出口是 `Map[obj, 出口]`），这条 L3 自己没写全，但方向对。
- `budget` 断言与 `jc lower` / `jc plan` 两份报告（§5）。
- `labels {…}` 静态标签集与 `.by_label` 覆盖检查（L1 的 `switch` 已有，统一语法）。
- `sink drop` 显式丢弃并记账（L1 只有 escalate/refine，缺「明确不管」这一支）。
- `ring` 允许**宿主计量做变式**（`variant host size(reg) decreasing`），直接解掉 L1 自评弱点 4（「未审差异数」硬配打分题）。变式是打分题只在「程度」不能由宿主算时才需要。
- 裂变按操作分别定义合回规则（L3 §2.1 的三种裂变 + L2 的 exists=max / 计数 / 锦标赛合回）。

**从 L2 嫁接：**
- `on / ctx / over / anchors` 的槽位名进 `state` 和题声明，程序员不拼字符串。
- E7「含同伴的打分不许排序」的编译期检查。
- 下沉表的形式（长度档 × K）与 >255 裂变再锦标赛的规则。
- **纯查询片段的规则形式**作为库级构造：在 `program` 内允许一个 `rules { … }` 块，只含无副作用的谓词合取（过滤、配对、存在/计数），编译成 L1 的 `for`+`if`，由规划器自由重排。副作用一律留在命令式语句里。这样 L2 的最大优点（规划器替人排顺序、程序最短：15 条 77 行）只在它安全的地方出现，它的最大弱点（`fn!` 进规则、成本藏起来）被排除在外。

**L1 自身必须补的语义（按 §1）：** 赋值语句；`for` 体只允许对累加器做可交换操作、迭代集合在体内只读、并发结果按程序点归位；无依赖的 `do` 允许并发且键为（程序点，参数哈希，迭代索引）；`refine` 定义为「当场对细拆片段递归求值，出口按当前守卫的三支归并，不改被迭代集合」；程序的返回类型带 unsure，调用方的守卫把它接进自己的 `unsure` 支；`select` 下沉为 K noul 时无 act 或并列 → unsure，K>16 段落级 → 分组锦标赛；集合渲染走 `canon` 规范顺序；置换种子由（渲染状态，题，次数）哈希导出。

补完这些，L1 加嫁接的东西就是一份可以直接开写解析器和解释器的规范。

## 7. 补充：`10-组合代数-v0.md` 的 16 种映射作为固定组合子，三套各怎么实现；? 的固定去向能否由运行时统一执行

### 7.1 逐格对照

映射 = 输出（位 / 索引 / 档）× 目标槽（材料 / 问题 / 候选集 / 刻度 / 动作 / 循环）。「可写」指用该设计现有语法能写出这一格；「缺」指语法上没有对应物。

| 格 | L1 守卫命令式 | L2 声明式 | L3 电路 |
|---|---|---|---|
| 位→材料（门） | `if q on m { 进 }` | `rule h :- P(x)` 过滤 | `.act -> state.obj` |
| 位→问题（门：问/不问） | 嵌套 `if`（编译器合并） | 体内字面顺序无语义，**缺**「先判再问」的保证 | 两层：`.act` 接下一层 state 再挂题 |
| 位→候选集（剔除） | `filter` 骨架后 `select` | `x in C, 可行(x)` | `.act -> state.cands` |
| 位→动作（执行/不执行） | `if q { do S }` | **缺**：`rule :- 值得跑(c), r = run!(c)`，`run!` 与守卫字面无数据依赖，规划器可先跑 `run!`；要加「体内 `fn!` 只对前面字面全为 act 的绑定执行」的左到右语义，这与它的重排自由冲突 | `.act -> S` |
| 位→循环（继续/停） | `while` 只接打分，**缺**位驱动的退出（要 `if q { break }`，文法无 break） | `iterate … until`？文法无 until，**缺** | `ring … until cond` 的 cond 是宿主表达式，接 `.act` 需先 `size(q.act) > 0`，可写 |
| 索引→材料（取） | `select … as x { 用 x }` | `x = 选(…)` 后用 x | `.pick -> state.obj` |
| 索引→问题（路由） | 题是值，`switch` 各支挂不同题，可写但要 K 支 | **缺**（谓词名不能当值，L2-4） | **缺**：题面是字符串字面量，不是线 |
| 索引→候选集（分支） | `switch` 各支给不同候选集 | 可写（各支各规则） | `.by_label -> state.cands` |
| 索引→刻度（换刻度） | **缺**（刻度不是值） | **缺** | **缺**（scale 不是线） |
| 索引→动作（分派） | `select … as a { do act(a) }` | `act!(下一步(s))` | `.pick -> S` |
| 档→材料（阈 / 前 k） | **缺** `if measure ≥ ℓ`（打分只能进 `while`）；前 k 靠 `rank` 骨架 | `s = 严重(d), s >= 中`、`order by`、`top k` | `.at(ℓ) -> state.obj`、`.order` |
| 档→问题（换题） | `switch` 在档上分支再挂题，可写 | **缺**（同路由） | **缺**（同路由） |
| 档→候选集（保留 ≥ℓ） | 同上缺 `if measure` | 可写 | `.at(ℓ) -> state.cands` |
| 档→刻度（缩放） | **缺** | **缺** | **缺** |
| 档→动作（分配） | 档是出口值，宿主按档分配，可写 | 宿主函数吃档，可写 | 宿主，可写 |
| 档→循环（变式） | `while … < ℓ bound n` | `iterate variant` | `ring variant measure` |

计数：L1 可写 11 缺 5，L2 可写 10 缺 6，L3 可写 12 缺 4。三套**共同缺**的是「问题槽」和「刻度槽」作为目标的四格（路由、换题、换刻度、缩放），原因一样：**题和刻度在三套里都不是一等值**（L1 半是：「题是值可传库函数」但没有从索引到题的映射语法）。这四格要成立，题与刻度必须能被线/变量携带——实现上就是让 `Q_test / Q_select / Q_measure / Scale` 成为可赋值、可放进集合、可被 `select` 当候选的类型。这一步不难（题是带校准 id 的字符串，刻度是带锚指纹的档位集），但三套都没做，而「下一问」题式（二阶推导）完全依赖它。

### 7.2 ? 的固定去向能否由运行时统一执行

`10` §3.2 的规则：? 的去向按**目标槽**固定（材料→细拆再判；问题→升级；候选集→再生成；刻度→加锚；动作→不执行；循环→退出记账）。要由运行时统一执行，条件只有一个：**运行时得知道这道判断的输出接的是哪个槽。**

- **L3 满足条件**：出口线的目标（`state.obj` / `state.cands` / `S` / `merge next reg` / `out`）在 `connect` 里写明，编译器能从目标推出槽，于是可以把 E-unsure（每条 `.unsure` 必须显式连接）改成「按目标槽默认连接，允许覆盖」。实现是编译器的一遍：对每个未连接的 `.unsure`，查它的兄弟出口（`.act` / `.pick` / `.at`）接到哪，按表插入 `refine` / `sink escalate` / 再生成 / 不接 / 退出。**最容易统一**。
- **L2 半满足**：unsure 已经是三值真值，运行时按强 Kleene 统一传播，不用程序员每处写——这是三套里唯一已经「统一」的。但它统一得太粗：所有 ? 都流到 `goal` 的一条策略，丢掉了按槽的区别（材料格该细拆、候选集格该再生成，它一律 escalate/keep/drop）。要按槽固定，规划器要在体内字面级别知道每个 ? 来自哪个槽（`on` 超窗 → 细拆；`over` 平局 → 再生成；`anchors` 不足 → 加锚），这是可做的，因为 L2 的槽是显式语法（`on / ctx / over / anchors`）。动作槽（`fn!` 不执行）与循环槽（退出）在 L2 里没有对应的语法位置，做不到。
- **L1 不满足**：`if q on m { do S }` 里，这道判断接的是材料槽（? 该细拆 m）还是动作槽（? 该不执行 S）？语句形状分不出来，所以编译器无法替程序员选去向，只能要求每处写 `unsure` 块——这正是 L1 自评的第一弱点，根源在这里，不在语法糖。

**统一执行的实现方案（适用于以 L1 为骨的收敛稿）：** 把 16 种映射做成**具名组合子**，每个组合子的目标槽在名字里（`gate` 材料/动作要分成 `gate_in` 与 `gate_do`，或按参数类型区分）：

```
gate(q, m) -> m ⊎ ∅            材料门；? → refine(m) 再判，细到单段仍 ? → escalate
run_if(q, m, S)                动作门；? → 不执行，记账
take(q, C, ctx) -> M           取；? → 若绑定了 gen 则再生成，否则 escalate
route(q, Qs, m) -> Q           路由；? → escalate
branch(q, C_by_label)          分支；? → escalate
dispatch(q, A, m)              分派；? → 不执行
threshold(q_measure, S, ℓ)     阈；? → refine 后再量，仍 ? → 计入 unsure 流
retitle(q_measure, Qs_by_level) 换题；? → escalate
keep_at_least(q_measure, C, ℓ) 保留；? → 保留进 unsure 流
rescale(q_measure, finer)      缩放；? → 加锚（参照库有）否则 escalate
allocate(q_measure, S, plan)   分配；宿主按档分配，? 档按最低档分配并记账
variant(q_measure | host)      变式；? → 退出并记账
```

三条实现规则：（1）组合子体内实现一次 ? 去向，程序员调用时**不写** `unsure`；裸的 `if / select / while` 仍强制写 `unsure`，所以「没有静默二值化」的保证不变——去向不是静默的，是固定且记账的。（2）「再生成」「加锚」两种去向依赖外部资源（生成器、参照库），组合子要有降级：资源不在就 escalate，编译期检查是否绑定。（3）每次按表走的 ? 去向写进账本与轨迹（`jv replay --layer` 能看到「此处 ? 按材料格规则细拆为 3 段」），这就是「预定义的编排」的可见性。

### 7.3 顺带发现：`10` §3.1 的第四、七行与实测规则冲突

「选 + 量」和「判 + 选 + 量」写成**同一状态一次调用**。但 E10 已定（L2 的 E7、L3 的类型规则 3 都照此写了）：打分状态不放同伴，含同伴的打分只能按出口计数、不能排序，也不能拿档去和选择题的索引做「一致性检验」。所以「优化步一次给齐」在**一次往返**意义上成立（选择题一次调用 + K 道各自单独状态的打分并发），在**一次调用**意义上不成立。建议 `10` §3.1 把「一次调用」改为「一层」，一致性检验改为「选择题的索引 vs 各自单独打分的最高档」。这不改变结论，只改变账本键的数量：K+1 个，不是 1 个。

### 7.4 对收敛的补充

- 收敛稿要把题与刻度升为一等值（`Q_*`、`Scale` 可赋值、可入集合、可作候选），否则 16 格里的 4 格与「下一问」题式永远写不出。
- 16 个具名组合子作为库第一层发布，替代 L1 里散写的 `if/select/while` 模式；组合子的目标槽固定，? 去向按 `10` §3.2 表在组合子体内实现一次。
- L1 还要补 `if` 接打分出口（`if 紧急 on m ≥ 高`）与位驱动的循环退出，补上后 L1 的 5 个缺格只剩「问题槽 / 刻度槽」两类，由一等值解决。
