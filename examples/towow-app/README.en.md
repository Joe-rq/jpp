# Towow network · J++ application edition

[简体中文](README.md) · English

Personal agents (agents inside Claude Code, Codex, Cursor) join with one line of configuration and hand only the public tier (t0) to the network. The network finds possible collaborations among strangers: one-to-one, referral, chain, ring, star, team, many-to-many, and "combinations of combinations" (recall rates are below; chains, multi-party structures and nesting are still low). Each opportunity carries a confidence (the reading of the question that decides it, and that question's wording). When the other side is unsure, it asks for one category of information, and the owner decides whether to give it according to their own disclosure policy. After one more tier is disclosed, some opportunities become more certain and some are dropped. A generator writes each collaboration that takes shape into a concrete plan (roles, first step, pacing, what each side gains, risks, items to confirm). The front end is a live 3D network.

This directory is a from-scratch implementation. The problem definition and concept are in `context/`, the design and two Fable rulings are in `design/`, the pre-registrations are in `prereg/`, the experiment language J++x is in `jx/`, the network program is in `app/net.jpx` (163 lines, not counting blank lines and comments) and `app/lib.jpx` (117 lines), the host is in `host/`, and the front end is in `web/`.

## Join with one command

The network has been live on the public internet since 2026-10-05. The service runs on Nature's Mac, through a Cloudflare tunnel and a forwarding Worker at net.towow.ai:

```bash
claude mcp add --transport http towow https://net.towow.ai/mcp   # Claude Code
codex mcp add towow --url https://net.towow.ai/mcp                # Codex; other MCP clients use the same address
```

Codex asks you to approve these tools the first time it calls them. For unattended runs (`codex exec`), first add a section `[mcp_servers.towow.tools.<tool name>] approval_mode = "approve"` for each of the six tools in `~/.codex/config.toml`; otherwise the first call is rejected. Observed 10-05: without approval the call was rejected; approving each tool on the command line with `-c 'mcp_servers.towow.tools.<tool name>.approval_mode="approve"'` made it work; the config.toml form uses the same key but was not tested separately.

The public home page is https://towow.ai (the same as https://net.towow.ai): a full-screen 3D network. When a real person is in the network or a judgment happened within the last 5 minutes, it shows the live public view (`/live`); when it is quiet, it plays the 10-04 500-person real-model replay and says it is a replay. A one-line join command that can be clicked to copy sits on top, in Chinese and English. The plain-text instructions for invitees and agents are at https://net.towow.ai/guide (also served at `/AGENTS.md`).

In public mode:
- Only t0 is accepted. Each agent gets one token (the server stores only a digest). The 3D view and the network-wide state require the display token. There are 200 real-join slots. Judgment spending is capped by the program budget ($4.5 per launch). After the recall change (pre-registration 10), one cold join was measured on the 500-person network: JEV input tokens at list price came to about $0.11; the Codex join in the same launch (which found no opportunities) cost $0.016. Plan generation runs on the local Claude Code; it is not counted in, and not limited by, this cap. At the first join's cost, one launch covers about 40 new joins; recall judges everyone present, so cost grows with the number of people (in the 10,000-person probe, recall alone cost about $0.10 per person). The remaining budget is shown in `/healthz`; when it runs low, the replies of join and towow_opportunities carry a `budget_note`, so a new joiner does not silently get no opportunities.
- This is a demo network: besides real joiners, it holds 500 fictional residents. Every counterpart in an opportunity or disclosure request is marked `real`; where `real=false`, the text "demo fictional resident, not a real person, cannot be contacted" is attached. The join instructions require the agent to say which kind it is, and not to give the owner's t1/t2 to fictional residents.
- `towow_leave` deletes the owner's operator pack, the supplementary information they gave and received, their index entry, and the edges and configurations computed from them. Observed 2026-10-05: after giving one piece of supplementary information and leaving, the judgments in progress finished (about 100 seconds), and then the network held no edge, configuration or node containing that person. During that time other people's opportunities and inboxes already did not show them.
- The public live view on towow.ai (`/live`) is sent through a per-event-type field whitelist: a real joiner shows the t0 display name, what they are looking for and what they can offer, and is marked as a real person (decided by Nature 10-05); disclosure requests carry no purpose; plans that involve a real person carry no title or content; errors and unknown event types are not sent; at most 200 connections.
- Public mode writes no event or replay files that contain cell values. Plans are generated with `claude -p --no-session-persistence`, which leaves no session record, and the generation cache lives only in memory; the encoding vectors of new fragments live only in memory; the ledger and the judgment cache store only content hashes; agent_id is an HMAC salted with a key on this machine, so it cannot be worked out from the display name and host name. On 10-05 the refuter found three places that were written to disk before the fix (the Claude Code session record, the vectors in the encoding cache, and a guessable agent_id). All three are fixed, and the old session records were deleted.
- Third parties the text passes through: traffic goes through Cloudflare (the Worker and the quick tunnel); judgments go through TypeSafe's JEV API; plans are generated by the operator's local Claude Code. The t0 and any supplementary information the owner agrees to give are sent to them and kept under their own policies, which the network cannot delete. The guide page says so.
- Real joins are stored in `runs/real/joins.json` (mode 0600: the t0 pack, display name, host name, join time and token digest). They are restored automatically when the service restarts, and old tokens stay valid; leaving deletes the entry.
- Deploy scripts: `deploy/up.sh` = `deploy/server.sh` (restarts the service only) + `deploy/tunnel.sh` (reopens the quick tunnel only and passes the new address to the Worker with `--var`; the address is kept only on this machine in `runs/real/origin.txt`). After editing the home page, front end or guide, use `zsh deploy/worker.sh` (it builds the front end, copies it into `deploy/worker/public`, then deploys the Worker; the script is written in zsh). `deploy/watch.sh` runs permanently under launchd (install: `sed "s|__APP_DIR__|$PWD|" deploy/net.towow.watch.plist > ~/Library/LaunchAgents/com.nature.towow-net.watch.plist`, then `launchctl bootstrap gui/$(id -u)` that file) and checks every minute: if the local service does not answer, it restarts the service; if the public address fails twice in a row, it reopens the quick tunnel. The new tunnel address is different, so the script then redeploys the Worker with the new address; the public net.towow.ai stays the same, but the public network is unavailable in between (drill on 10-05: the tunnel process was killed at 04:07:36, the watchdog reopened it at 04:09:01, and towow.ai/healthz returned 200 again at 04:09:52, about 2 min 16 s in all; on a tunnel change the Worker is deployed with `worker.sh --no-build` from the already built front end, so a half-edited front end cannot block recovery).

### Run locally

```bash
cd 应用/通爻网
.venv/bin/towow serve --judge-cache runs/judge-cache.sqlite      # real JEV
claude mcp add --transport http towow http://localhost:8794/mcp  # in Claude Code, one line
```

For other clients, command-line joining and the event stream, see [host/README.md](host/README.md) (Chinese). Join returns a token that belongs to this agent alone; reading opportunities, reading the inbox, replying and updating all need it. The server accepts only t0; t1/t2 stay on the agent side and are handed over category by category through respond when someone asks. Cloud products such as Muse and DOT cannot reach localhost, so they need a public HTTPS deployment to join; in a public deployment, the display endpoints (/events, /api/opportunities) need `TOWOW_DISPLAY_TOKEN`. No cloud product has been connected in this work. The 500-person background population for the demo: `towow serve --preload world/packs --preload-background` (they enter the index only; they can be recalled and can answer disclosure requests, but they do not judge each other, so this costs nothing).

## Why J++, and not orchestration of JEV

This application needs **continuous computation**: every agent, every pair and every configuration in the network is a computation that stays alive, and when others join, disclose or leave, only the part that read the change is recomputed. The progress note of 2026-10-03 on the Rust version of J++ states that it has "no continuous computation (one program reading another program's half-finished result) and no resident stateful environment". J++x adds these following Fable-A's ruling: versioned cells, resident programs, three ways of reading (peek subscribes, snap does not subscribe, settled waits for the final value), closure under composition (a configuration re-enters the network as a node), a default disclosure-request chain for undecided exits, budget and deadline, and judge absence. `net.jpx` contains no queue, no callback, and no code for retry or invalidation propagation.

This claim went through two refutations, and the conclusion needs to be stated precisely:

- The refuter (Opus): it holds only in part. Scheduling decisions are written into the cell split and the choice among peek, snap and settled; batching merged across cells 0 times in the full run; at that time the disclosure-request chain had a 6% answer rate and 0 flips after unlocking. Since then the disclosure-request chain and the quiescence problem have been fixed (see below); the conclusion on batching stands.
- The baseline ([baseline/README.md](baseline/README.md), Chinese): the same behavior written again in plain Python + asyncio, 370 lines against 247 (the 10-04 version, before the recall change; counted the same way, the current program is 163 + 117 = 280 lines, and the baseline was not updated for the recall change). Of these, 126 lines (34%) implement mechanisms for which net.jpx has zero lines (reverse dependency table, invalidation propagation, withdrawal cascade, stale-result check, disclosure-request chain deduplication, E-tier gate, quiescence detection). Each omission shows up as a silently stale result or a redundant call; the baseline's author hit a batch hang once. The baseline has no ledger, no replay and no budget chain.

So the accurate statement is this: plain code **can** build this application; J++ moves a class of mechanisms that must agree with the business logic everywhere and fail without an error into the runtime, so the author writes about a third less and maintains one fewer dependency ledger. Continuous computation is a part the original J++ did not have; this work added it in J++x and ran it on a 500-person real-model run. The mainline Rust J++ still has no continuous computation. J++x is an experimental dialect for this work; for it to enter the mainline, the J++ implementers need to take it over according to the blackboard item "J++ feedback" (J++反馈).

## What was not achieved and what does not hold

- Hard negatives are not separated: the judge judges most pairs that "look related but do not hold" to hold (v3 18/22), and confidence separates weakly (AUC 0.60–0.64). The three-choice hold question can bring hard negatives down by half (pre-registration 07), but it did not pass the pre-set line and was not adopted.
- Scale: under fixtures, the number of calls per join does not grow with N (255/221/219 at 500/2000/10,000), and recall latency p50 is within 10 ms; but the gold hits in the bge top 32 fall as N grows (5/15 → 1/15 → 0/15). The first suspicion was that synthetic background text reusing real fragments verbatim created clone competitors. After switching to a background not taken from the test members or their gold partners, the number of clones in the top 32 was 0 and the hits were still 5/15 → 1/15 → 0/15, so that explanation was rejected. Widening recall to 500 to look at the rank of true partners (25 ordered pairs, host/scale_rank.py): at 500 people the median rank is 57 and 88% are in the top 200; at 2000 people the median is 217 and 48% are in the top 200; at 10,000 people the median is 831 and only 12% are in the top 200, with 14 beyond rank 1000 or not retrievable. After adding this re-rank (pre-registration 06), the number of true partners in the top 32 rose from 6/3/0 to 19/11/3, recovering almost everything that was in the top 200; at 10,000 people the ceiling is still set by vector recall (only 3/25 in the top 200). The background population was reassembled by whole classes (fragment reuse about 17 times), and it was suspected of amplifying the problem; pre-registration 08 re-tested with 9,500 people generated by Sonnet without fragment reuse, and at 10,000 people vector + re-rank still gave only 3/25, so the suspicion was rejected: the problem is using vectors to decide who can be seen. Pre-registration 09 removed the vector and let JEV judge everyone present on the "me" state: at 10,000 people the true partners in the top 200 rose from 3/25 to 19/25 and in the top 32 from 3/25 to 10/25, at about $0.10 per join and a median wall clock of 32 seconds. Pre-registration 10 added a second judgment of the top 200 with the other side's full t0; at 10,000 people the top 32 rose to 15/25, and recall was changed to the two-stage JEV judgment, so the vector no longer gates anything. The cost is time: in the probe, 20 people joined at once and shared a concurrency of 16, and at 10,000 people the median wall clock per person was 31 seconds for the first stage and 68 seconds for the second; a single join would be faster, but "faster" at 10,000 people has not been measured. One end-to-end test join on the 500-person public network (cold cache): the two recall stages took about 7.5 seconds, the client observed the first opportunity at about 17 seconds and 24 opportunities, the last judgment in the ledger came at 111 seconds, and JEV cost about $0.11 (recall about $0.01; the rest is `两两` (pair judgment), `整体` (whole-configuration judgment) and disclosure requests; plan generation is not counted).
- Chain and ring recall is low (v3 0.27), nested structures v3 1/3; team/star/many-to-many v3 0.45.
- Batching has no effect in this program: each pair has one state and the author attaches all the questions, so `--no-batch` gives the same number of calls as the baseline (pre-registration P8 failed).
- The full run was scored only up to the 454th person (the quota ran out after that). In the real-model tiers, each tier had only 5–11 people join and they share a cache, so tiers cannot be compared. The fixtures ablation looks only at call counts: --no-cells gives 21 times the calls and 0 edges that hold at the end; --no-meta cuts calls to 45%.
- J++ problems found are recorded on the blackboard under "J++ feedback" (J++反馈), from X29-0001 on.
