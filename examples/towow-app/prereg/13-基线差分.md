# 预注册 13 · 基线差分：普通 Python 基线与 J++x 跑同一条事件轨迹（先于代码与运行）

日期：2026-10-05，写于基线改动、差分工具和任何运行之前。全部用 fixture 判断器，不花 JEV 钱。

## 要回答的问题

10-05 最终验收反驳第 1 条：「只有 J++ 才能做」被本项目自己的基线否定，基线也没有和 J++x 跑过同一条事件轨迹。它要的证据是：同一轨迹上，手写版本出现陈旧结果、挂死、多余调用或漏撤回，而 J++x 没有。本次把这件事测出来，测出什么写什么。

## 已经看过的结果

- 基线 `baseline/net_py.py` 写于 10-04（提交 5806b00d1），之后 net.jpx 改过五次，基线一次没跟：宽召回 + 重排（015323063，预注册 06）、离开撤回（efe496542）、两段全量召回（ea06824b7，预注册 10）、方案门（fcc7118a5，预注册 11）、草案定义（52a5a49ed）。
- 这几次需求变更在 J++ 一侧改了多少（按 README 口径：去掉空行与注释的行，加 / 删）：

| 需求 | 程序（net.jpx + lib.jpx） | 运行时（jx/） |
|---|---|---|
| 召回改两段全量（含先前的宽召回 + 重排） | +37 / −9 | +25 / −3（sched.py 按 token 切批，真机 100 道长题超上限才需要） |
| 离开撤回 | +5 / −0 | 0 |

- 基线自己有离开撤回（10-04 就写了 `leave`、`_drop_pair`、`_kill_cand`、`_retract_cfg`）；J++x 一侧是 10-05 公网实测发现「settled 读已撤回的 material 会一直等」后才补的。
- 读过的 J++x 运行时行为（只读，不改）：撤回造成的删除推迟到全网静止才发布（engine `_deferred`）；提交后若读过的单元又变了就再跑一次（`_commit` 末尾），也就是先写后重算；`union` 单元（inbox、cand、hits）不随撤回删除，`views.inbox` 在展示时按 world 过滤。

## 假设

H1（系统级）：基线补到与现行 net.jpx 同语义后，在同一条不等静止的事件轨迹上，两边静止后的终态一致，且都与按最终输入算出的真值一致。也就是说「普通代码做得到」在这条轨迹上成立，差别落在代价上。

H2（系统级）：基线里手写的每一处依赖登记都是承重的：去掉其中一处，至少一个检测项会在终态抓到错误，而且这类错误不报错。J++x 程序里对应的代码是零行。

H3（描述）：两边在过程中的代价形状不同：J++x 先写后重算、删除等静止，过程里写出的陈旧值和离开者的可见残留更多；基线发批时不再查缓存，可能有重复发送。

## 设计

### 基线补齐（改 `baseline/net_py.py`，逐项记行数）

1. 召回：`present` 给出在场全体 → 在「我」的状态上一段粗判（题面同 `rerank_q`）→ 前 200 用完整 t0 再判（`rerank_q_full`）→ 前 32 进两两；构型节点走向量 40 → 一段判 → 前 8。
2. 方案门（预注册 11）：两人构型不问整体，hold 取两两的决定性题（edge 不成立即不成立）；新增 `best[m]`；方案门改为「每位成员都把它排进前 2」，去掉 0.6；有成员一层都没向其他成员放行时标草案。需要的新依赖：edge → 两人构型、best[m] → 含 m 的方案、unlocked → 方案。
3. 离开：对齐宿主 `server.leave`（删 world、索引、含他的 unlocked 与 reply），并把 best 与方案纳入撤回。
4. 只为能跑同一判断器做的接口适配（读数带 p、选择题带标签），单列，不计入需求变更。

每一项分开做、分开数（scratchpad 里留中间版本，数完删掉），与上表 J++ 一侧并列。

### 判断器

同一个确定性规则函数，两边各一层薄适配（J++x 走异步端口，基线走 `Ports.judge`）。读数只依赖状态内容，所以披露会改变读数：

- 每人的公开层是 `need:X`、`offer:Y` 形式的片段；两两里「B 能帮 A」当且仅当 B 可见的 offer 与 A 可见的 need（t0 加这一对已解锁的片段）有交集。成立时开放题读数在 0.66–0.95，按这一对的内容哈希取值、各对不同；不成立时 0.10–0.29。形式题有交集选 direct，否则 none；方向题按两边交集选 ab / ba / both / none。
- 构型节点一侧的开放题一律不成立（它的向量召回依赖时序，不进严格比较）。
- 多人构型的「能成吗」：成员之间按可见片段的互补关系连通、且每人至少有一条互补时成立，读数按成员集合哈希取 0.66–0.95；「去掉某人」答否；成长的「更紧密」答否。
- 召回两段：互补 0.9，否则 0.2。
- 是非题读数一律避开 0.4–0.6，补信息默认链（读数落在 0.5 附近才触发）在两边都不触发。披露只经宿主事件：两位 `real=true` 的居民给出（`unlocked` + `reply`，同 `server.respond`）或拒绝；材料更新是改写 world（t1 提为 t0、加一条 offer、删一条 offer）。

### 轨迹

- 30 个 id，任何时刻在场不超过 30 人（≤ 33，召回的前 32 截断不会生效；两段召回只在调用数上被测到，不在挑人上被测到）。结构稀疏，每人的构型候选不超过 6 个（`take(novel, 6)` 不截断）：6 对互补、3 条三人单向链、2 位真实接入者各有一位只在 t1 才对得上的伙伴、2 位靠材料更新才对得上的人、若干孤立者。
- 约 70 个事件：全部接入（种子打乱顺序），中间穿插真实接入者的给出与拒绝、材料更新（提层、加 offer 使某人多出一个更强的构型、删 offer 使一个两人构型解体）、离开（互补对的一方、链的中段、一位给出过补充信息的真实接入者）、再接入（其中一人换了材料）、再更新。
- 事件之间不等静止：每个事件后让出 0–40 次事件循环（种子决定）；判断端口每次调用内部再让出 0–5 次（按状态哈希）。全程不用墙钟睡眠，同一种子可复现。最后等静止，墙钟上限 120 秒。
- 种子 0–4，每个种子两边各跑一次。

### 场景

- S2：同一轨迹，判断端口在第 40–42 次调用抛异常（模拟判断器缺席三次），之后恢复。
- 注入（只在基线上，在 `baseline/diff/` 里用子类覆盖，不动 `net_py.py`）：
  - I1：材料变了不再让两两重算（`_material_changed` 不标两两）

  - I5：两两提交前不查 `stale()`
  - I6：静止计数错一处（`judge_many` 挂起时不减 `busy`）

| 类 | 检测项 | 怎么数 |
|---|---|---|
| 终态错误 | 边与真值不一致 | 静止后，在场两人的每一对按最终输入用规则算出 holds、dir、form、决定性读数，与系统存的比 |
| 终态错误 | 构型无效 | 有成员不在场；两人构型的 edge 不成立或读数 ≠ 决定性读数；多人构型按最终材料不成立 |

## 判据

- P1–P3 全中：H1 成立。README「为什么要 J++」那段照实写：同语义补齐后普通代码在这条轨迹上没有出错；差别在每次需求变更要改的行数、要手登的依赖，以及注入实验里哪些遗漏终态静默。不写「只有 J++ 才能做」。
- P1 或 P2 不中且错在基线：照实写出基线出错的类型与触发的事件，这是「手写会出错」的证据；同时查是不是补齐时自己写错（补齐错误也算手写代价的一部分，但要分开说）。
- P1 或 P2 不中且错在 J++x：记 J++ 问题交主会话登黑板，README 不得写 J++x 更可靠。
- P11 里有注入终态抓不到：说明那处依赖在这条轨迹上不承重，照实写，不为抓到它改轨迹。
- P10 只说明基线没做「缺席后重判」这一项机制（基线 README §3 已承认），不作为同语义下基线出错的证据。

## 已知的偏差

- 只有一个规则判断器，读数离 0.5 都远：补信息默认链、near_band、截止与预算两边都没被测到。真判断器的读数会挤在 0.5–0.65（预注册 11），这条链在真实运行里是常态。
- 在场人数 ≤ 30：召回的前 32 截断、1 万人时的依赖粒度都不在这次范围内。
- 构型节点的边一律不成立：组合的组合不进严格比较，只查它在成员离开后是否撤干净。
- 交错由事件循环让出次数决定，覆盖不了真实网络时延下的全部顺序；五个种子是抽样，不是穷举。
- 基线由我补齐，写法与桩的粗细会影响行数；行数只作量级。

### 按判据

- 基线一侧 H1 成立：补齐语义后的普通 Python 在五个种子上终态与真值逐项一致，不挂死，补齐时写的代码没有被查出错。「普通代码做得到」在这条轨迹上测实了。
- P2 不中且错在 J++x：按判据记为 J++ 问题交主会话，README 不写 J++x 更可靠。

### 发现的 J++ 问题（交主会话登黑板）

1. **静止前再接入会永久丢边。** 一方离开时，宿主删 world，运行时把 material 的删除推迟到全网静止（engine `_deferred`）；网络一直在算时，他以同样材料再接入，推迟的删除被取消，material 值和版本都没变，他的召回不重跑。离开期间别人的召回重跑过（`present` 里已经没有他），由那次召回派生的两两被撤掉，之后没有人再派生它。主轨迹里丢的恰好都是不成立的对，最小复现（`baseline/diff/test_diff.py::test_jpx_rejoin_before_quiet_restores_pair`，xfail）里一对互补的人的成立边永久消失；先等静止再接入就不丢（`test_jpx_rejoin_after_quiet_restores_pair`）。基线没有这个错。公网也会碰到：`host/server.py` 的 agent_id 由称呼与宿主名算出，再接入是同一个 id；world 里多出的 `joined_at` 不进 material，同一个包再接入时 material 不变。
2. **离开者在静止前一直留在计算里。** 同一个推迟让 `peek material == unit` 的离开检查在静止前不生效：两两、整体继续拿离开者的公开层去判断（每个种子 8–20 次调用，基线 0–1 次），他的成立边在别人那里一直可见（27–39 次观察，基线 0）。两边都有离开者自己的召回在离开后才发出（J++x 22–24 次，基线 29 次），那是离开前就登记好的批。公网说明里「进行中的判断走完后撤回（约 100 秒）」只在网络会静下来时成立；持续有人接入时，离开者的文字在静止前还会继续发给判断器。
3. 记录、不算错：伴随题每批都发，这条轨迹上每个种子 1694–1765 道、一道没用上（读数都离 0.5 远），约占题数的 17%；这是「伴随题并行问」的设计，真机上是花费。union 单元（cand、hits）不随离开删除，展示层按 world 过滤。
