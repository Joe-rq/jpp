# net.jpx 的普通 Python 基线

问题：J++ 是否只是对判断 API 的简单编排？做法：用普通 Python + asyncio 写一个与 `app/net.jpx` 行为等价的实现（`net_py.py`），判断、召回、图算法、生成器用桩（`Ports`），其余全部手写，如实统计。

运行：`.venv/bin/python -m pytest baseline -q`（3 个测试，假判断器，不花钱）。

## 2 我手写的、J++ 运行时替 net.jpx 做的事

net.jpx 开头写明「本文件里没有一行调度代码」。下表是 Python 版里对应的代码，行数按函数统计（含少量重叠）。

| 机制 | 行数 | 代码 | 容易写错的地方 |
|---|---|---|---|
| 依赖追踪 | 约 25 | `pairs_of`、`cands_of`、`grow_deps` 三张手写反向表 + `_material_changed` | 每新增一个读者要想起去登记；`_grow` 读了候选 x 的材料，漏登记 `grow_deps` 则 x 变了不重算成长，且不报错 |
| 失效传播 | 7 + 散落 22 处 `mark()` | `_material_changed`、各处 `mark` | 漏一处 `mark` 就是静默的陈旧结果；多一处就是重复调用。测试里去掉 `_material_changed` 里对两两的 mark，增量测试会红（变异验证过） |
| 撤回 | 36 | `leave`、`_drop_pair`、`_kill_cand`、`_retract_cfg` | 级联：离开者 → 对 → adj/derived → 构型 → 以该构型为成员的构型 → 方案；顺序不对会留下指向已不存在节点的 adj 或 cand |
| 重跑与过时结果 | 21 | `mark`、`_run`、`rerun` 集合、`stale()`（6 处） | 单元在 await 判断期间输入又变了：必须在提交前查 `stale`，漏查则旧结果覆盖新结果。这是最隐蔽的一类 |
| 合批 | 48（与缓存、E-tier 合计） | `judge_many`、`parked`、`_kick`、`_flush` | 「所有单元都在等判断时才发批」靠 `busy` 计数；我第一版在判断端口抛异常时 flush 任务死掉，所有等待者永远挂起，整个网络不静止，测试直接卡死（真实踩到的 bug） |
| 缓存键 | 3 | `(h(状态), 题)` | 状态里混进不稳定字段（时间、排序不定的集合）则永远不命中；`derived` 须排序后再进状态。变异验证：删掉缓存检查，测试变红 |
| 补信息链 | 26 | `_request`、`_put_reply`、`_disc`，`_pair` 里约 8 行 | 请求要去重（持有方 + 请求方 + 类别），否则重判一次要一次；回复被改后「已解锁」要由全部回复重建（net.jpx 注释记录了同类错误：一对重判 25 次） |
| 截止 / 预算 | 6 | `wait_for` 超时 → 未决(deadline)；`calls_left` 耗尽 → 未决(budget) | 这类未决不该进缓存（下次应可重判）；我的实现把它缓存了，见 §3 |
| 深度 | 约 6 | `_whole` 中 `depth = 1 + max(成员层)`，≥ 上限则不发布 | 层数要沿构型嵌套携带；`invalid_candidate` 再单独限两层 |
| E-tier | 7 | `_etier` 在每次 `judge` 前检查 | 要在每条进状态的路径上都过这道闸；变异验证：删掉调用，测试变红。J++ 里是运行时拦在判断前 |
| 静止判定 | 5 | `busy`/`queue`/`parked`/`flushing` 全为空 → `idle` 事件 | 计数在 `await` 前后各加减一次，错一处就是死等或提前静止 |
| 同值不升版本 | 散落约 10 处 `!=` 比较 | `_pub`、`_pair`、`_put_reply`、`_whole` | 漏比较 → 下游无谓重算，网络可能不静止 |

以上合计约 126 行纯机制（占 net_py 的 34%），加散落的 `mark`/`stale`/比较约 35 行。

## 3 我没做到或简化了的

- 合批没有按「截止最近 → 事件最新 → 价值密度」排序，只有并发上限 32；`gen` 不参与静止判定这条也没做。
- 预算只有总调用数，没有按接入事件派生、只收紧的预算链；截止是单次调用超时，没有「截止时发布进行中的部分值与 progress」。预算 / 截止造成的未决我放进缓存，之后不会自动重判。
- 深度：只管构型嵌套层数，没有「沿触发链携带层数」的通用机制。
- 未决时的持有方：由判断器读数里的 `needed=(类别, 持有方)` 给出，缺省取第二方；J++ 里由运行时按题的 owners 决定。
- 「进行中」读：J++ 里 `settled` 未定下则发布进行中的部分值，下游 `peek`。我的两两在回复到来前直接按现有读数发布一次，再靠重跑修正。
- 没有账本、重放、带种子的确定调度、taint、归约器单写者检查（R7）、`claim` 占用。
- 召回命中只累积不撤销（对应 union 单元语义），没有逐键失效。
- **没有对 net.jpx 做差分测试**：等价性靠逐行对读，不是跑出来的。我也不能保证 J++ 的 `settled`/`peek` 重算顺序在边角情况与我一致。
- 防环（派生片段不进判断材料）两边都靠作者自己遵守：net.jpx 注释写了，我的 `_pub` 也只是同样排除；我没验证 J++ 的静态检查能否抓住违反。

## 4 net.jpx 里同样是作者在手写调度的地方（公平起见）

- `peek` / `snap` / `settled` 的选择就是调度决策：`两两` 用 `peek hits`，`构型` 用 `snap adj[y]`、`snap cand`，选错就多触发或漏触发。`on [...]` 里五个来源是手列的依赖。
- 扇出上限全是作者定的：召回 32（构型节点 8）、`take(novel, 6)`、成长 3 个候选、构型 `chain/ring/star/team/m2m` 的 limits。
- 注释里记录的几次修复都是失效/撤回语义的坑，不是业务错：「每次重算都把回复重写一遍（single 单元里没重写的写会被撤回）」、`cand` 改 union 以免整体被撤回、一对重判 25 次、gate-50b 披露 35619 题。运行时接管了机制，没有消灭对机制语义的理解成本；这些只在 60 agent 账本上才暴露。
- `derived` 不进 `material` 的防环、`fresh()` 去重、`invalid_candidate` 谓词，都是作者代码。

## 5 结论

J++ 与普通 Python 的差别不是「做不到」：同一组行为我在约 370 行、约一小时写出来并通过测试（接入、披露、离开只重判受影响的对，缓存、E-tier、补信息链、深度、静止都成立）。差别在代价与出错面。

- 写量：总行数 1.5 倍；其中 126 行（34%）是 net.jpx 里零行的机制，业务逻辑两边接近。
- 出错面：Python 版有 6 张手写的反向表/标记集合、22 处 `mark`、6 处 `stale` 检查、10 处同值比较，每一处遗漏都表现为静默的陈旧或多余调用，不报错；我自己踩到一个（端口异常导致批挂死）。J++ 把这些收到运行时一处，作者面对的是 `peek/settled/snap` 的取舍与扇出上限（§4）。
- 但这不构成「J++ 才能做」的证据，也未证明运行时实现本身没有同类错误（§4 的修复记录说明它也踩过）。能支持的主张是：同等行为下，作者少写约三分之一、少维护一套必须与业务逻辑保持一致的依赖账。该数字取决于我的写法与桩的粗细，应当当作量级而不是定值。
