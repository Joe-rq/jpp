# 通爻网 · J++ 应用版

简体中文 · [English](README.en.md)

个人 agent（Claude Code、Codex、Cursor 里的 agent）用一行配置接入，只把公开层（t0）交给网络，网络在陌生人之间找出可能的合作：一对一、转介、链、环、星、团队、多对多，以及「组合的组合」（召回率见下，链、多方、嵌套都还低）。每个机会带置信度（决定它的那一道题的读数和题面），对方拿不准时会来要某一类信息，主人按自己的披露策略决定给不给；多给一层后有的机会变得更有把握，有的被放下。成形的合作由生成器写成具体方案（角色、第一步、节奏、各自收获、风险、待确认事项）。前端是实时 3D 网络。

本目录是一次从零的实现：问题定义与构想在 `context/`，设计与两份 Fable 裁定在 `design/`，预注册在 `prereg/`，实验语言 J++x 在 `jx/`，网络程序在 `app/net.jpx`（不计空行与注释 183 行）与 `app/lib.jpx`（117 行），宿主在 `host/`，前端在 `web/`。

## 一条命令接入

已经开在公网（2026-10-05 起，服务跑在 Nature 的 Mac 上，经 Cloudflare 隧道与 net.towow.ai 上的转发 Worker）：

```bash
claude mcp add --transport http towow https://net.towow.ai/mcp   # Claude Code
codex mcp add towow --url https://net.towow.ai/mcp                # Codex；其他 MCP 客户端填同一个地址
```

Codex 第一次调用这些工具时会请你批准；无人值守运行（`codex exec`）时要先在 `~/.codex/config.toml` 里给六个工具各写一节 `[mcp_servers.towow.tools.<工具名>] approval_mode = "approve"`，否则第一个调用就被拒。10-05 实测：不放行时被拒；在命令行用 `-c 'mcp_servers.towow.tools.<工具名>.approval_mode="approve"'` 逐个放行后跑通；config.toml 写法是同一个配置键，没有单独实测。

公开首页是 https://towow.ai （与 https://net.towow.ai 相同）：全屏 3D 网络，网里有真人或 5 分钟内有判断时放实时公开画面（`/live`），安静时放 10-04 的 500 人真机回放并写明是回放；上面压一行可点击复制的接入命令，中英双语。给被邀请人与 agent 的纯文本说明在 https://net.towow.ai/guide （也在 `/AGENTS.md`）。

公网模式下：
- 只收 t0；每个 agent 一个 token（服务端只存摘要）；3D 展示与全网状态要展示 token；真实接入名额 200；判断花费受程序 budget（$4.5/次启动）封顶。改召回后（预注册 10）在 500 人网络上实测过一次冷接入：JEV 输入 token 按标价约 $0.11；同一次启动里的 Codex 接入（没找到机会）$0.016。方案生成走本机 Claude Code，不计入、也不受这个上限约束。照第一次的花费，一次启动约够 40 次新接入，但那次成立边很少。预注册 12 用原包冷接入实测：500 人时每人 $0.13–0.33，1 万人时 $0.53–1.05，八成以上花在组合封闭的级联上；预注册 16 给每条宿主事件链的级联设了 60 次调用的上限（按读数排序、用不完的挂起到下一次事件）之后，同一批人 500 人时每人 $0.044–0.051，1 万人时 $0.093–0.149（召回约 $0.09）；若每人花费不随接入次数上涨，一次启动在 500 人时约够 90 次接入，1 万人时约 30 次，但这 4 位里每人花费是逐位上涨的。公网服务（8794）还跑着旧代码，这些数要在它重启之后才适用。预算余量在 `/healthz` 里，快用完时 join 与 towow_opportunities 的回复带 `budget_note`，不让新接入者静静地拿不到机会。
- 这是演示网络：除真实接入者外有 500 位虚构居民。机会与补信息请求里的每一位对方都标 `real`，`real=false` 的附「演示用虚构居民，不是真人，无法联系」；接入说明要求 agent 讲清是哪一种，不把主人的 t1/t2 给虚构居民。
- `towow_leave` 删掉主人的算子包、给出过与收到的补充信息、索引条目和由此算出的边与构型。离开引起的撤回即时生效（预注册 15）：此前运行时把删除推迟到全网静止，持续有人接入时离开者还会被继续判断（预注册 13 查出）；改后差分五个种子漏边 0，离开者在途可见由每种子 27–39 次降到 0–13 次。
- towow.ai 的公开实时画面（`/live`）按事件类型的字段白名单发出：真实接入者显示 t0 的称呼、在找、能提供，并标为真人（Nature 10-05 定）；补信息请求不带用途，含真人的方案不带标题和内容；错误与未知类型不发；最多 200 个连接。
- 公网模式不写带单元值的事件与回放文件；方案生成用 `claude -p --no-session-persistence`，不留会话记录，生成缓存只放内存；新片段的编码向量只放内存；账本与判断缓存只存内容哈希；agent_id 是用本机密钥加盐的 HMAC，不能由称呼与宿主名反推。10-05 反驳者查出修复前三处落盘（Claude Code 会话记录、编码缓存里的向量、可猜的 agent_id），已改，旧的会话记录已删。
- 文字会经过的第三方：流量经 Cloudflare（Worker 与快速隧道）；判断走 TypeSafe 的 JEV API；方案由运营者本机的 Claude Code 生成。t0 和同意给出的补充信息会发给它们，按它们各自的政策保留，网络删不到。说明页写明了这一点。
- 真实接入存到 `runs/real/joins.json`（0600：t0 包、称呼、宿主名、接入时间与 token 摘要），服务重启后自动恢复，旧 token 照旧有效；退出时删除这一条。
- 部署脚本：`deploy/up.sh` = `deploy/server.sh`（只重启服务）+ `deploy/tunnel.sh`（只重开快速隧道，用 `--var` 把新地址交给 Worker；地址只记在本机 `runs/real/origin.txt`）；改了首页、前端或说明时用 `zsh deploy/worker.sh`（先构建前端，拷进 `deploy/worker/public`，再部署 Worker；脚本是 zsh 写的）。`deploy/watch.sh` 由 launchd 常驻（安装：`sed "s|__APP_DIR__|$PWD|" deploy/net.towow.watch.plist > ~/Library/LaunchAgents/com.nature.towow-net.watch.plist`，再 `launchctl bootstrap gui/$(id -u)` 这个文件），每分钟检查：本机服务不应答就重启服务，公网连续两次不通就重开快速隧道：新隧道地址不同，脚本随即用新地址重新部署 Worker，对外的 net.towow.ai 不变，期间公网不可用（10-05 04:07 演练：杀掉隧道进程，04:09:01 看护发现并重开，04:09:52 towow.ai/healthz 恢复 200，共约 2 分 16 秒；换隧道时 Worker 用 `worker.sh --no-build` 部署已构建好的前端，工作区里改了一半的前端不会挡住恢复）。

## 为什么要 J++，而不是对 JEV 的编排

这个应用需要的是**持续计算**：网络里每个 agent、每一对、每个构型都是一直活着的计算，别人接入、披露、离开时，只有读到变化的那部分重算。J++ 的 Rust 版在 2026-10-03 的进度里明确写着「没造：持续计算（一个程序读另一个程序算到一半的结果）、常驻有状态环境」。J++x 按 Fable-A 裁定补上这些：版本化单元（cell）、常驻程序（resident）、三种读法（peek 订阅、snap 不订阅、settled 等定稿）、组合封闭（构型作为节点再进网络）、未决出口的默认补信息链、预算与截止、判断器缺席。`net.jpx` 里没有队列、没有回调、没有重试与失效传播的代码。

这一主张经过三次检验，结论要说准：

- 反驳者（Opus）：只部分成立。调度决策写进了单元拆分和 peek/snap/settled 的取舍；合批在全量里跨单元合并 0 次；当时补信息链答复率 6%、解锁后翻转 0 次。此后补信息链与静止问题已修（见下），合批的结论不变。
- 对照基线（[baseline/README.md](baseline/README.md)）：用普通 Python + asyncio 把同一组行为写了一遍，10-04 写成时 370 行对 247 行；10-05 补到现行语义后 425 行对 300 行（net.jpx 183 + lib.jpx 117），其中 126 行（34%）是 net.jpx 里零行的机制（依赖反向表、失效传播、撤回级联、过时结果检查、补信息链去重、E-tier 闸、静止判定），每一处遗漏都表现为静默的陈旧结果或多余调用；基线作者自己踩到一次批挂死。基线没有账本、重放和预算链。
- 差分测试（预注册 13，[baseline/diff/](baseline/diff/)）：基线补到现行语义（两段召回 +29/−5 行、方案门 +35/−8 行；J++ 程序同两次需求净改动 +31/−3、+22/−2），两边用同一个确定性规则判断器、同一条不等静止的事件轨迹（30 人、52 个事件：接入、给出、拒绝、材料更新、离开、再接入），五个种子，按最终输入算出的真值逐项核对，不花钱。基线五个种子终态全对、不挂死。J++x 五个种子的成立边、构型、方案与基线逐项相同，但每个种子漏了 3–9 对边：一方离开后、在全网静止前以同样材料再接入，离开期间被撤掉的两两不再恢复（运行时把撤回造成的删除推迟到静止，再接入时值和版本都没变，召回不重跑）；这次漏的恰好都是不成立的对，最小复现里一对互补的人的成立边永久消失。同一个推迟让离开者在静止前一直被判断、一直可见。在基线上去掉一处手登依赖（材料变了让两两重算、edge → 两人构型、best → 方案），五个种子终态都静默出错；静止计数错一处就挂死。

所以准确的说法是：这个应用用普通代码**做得到**，补齐语义后在同一条事件轨迹上也做对了，「只有 J++ 才能做」不成立。J++ 的作用是把一类必须与业务逻辑处处一致、漏了也不报错的依赖登记收进运行时：方案门这一次需求，基线要手动补登四处依赖，net.jpx 一处不用写，而注入实验说明漏掉其中任何一处终态都会静默出错。两次需求变更基线改了 +64/−13 行，J++ 程序按净改动 +53/−5（逐次提交相加 +60/−12），基线多约三成；总行数基线 425 对 J++ 300，少约三成。运行时替作者做这些事，它自己也会错：上面的再接入漏边是 J++x 有、基线没有的错，已交「J++反馈」。持续计算这一块是 J++ 原有版本没有、这次在 J++x 里补上并在 500 人真机上跑通的。主线 Rust 版 J++ 仍然没有持续计算；J++x 是这次的实验方言，要进主线需要 J++ 实现方按黑板「J++反馈」接手。

## 结果（真机 JEV，2026-10-04）

下表全部是**改召回之前**（向量前 200 + 重排）测的。2026-10-05 召回改为 JEV 两段判断在场全体（预注册 10）之后的证据有三份：1 万人背景下 25 对真伙伴的探针（前 32 由 3/25 到 15/25，背景没有真值）；500 人公网上的一次冷接入（客户端观察第一个机会约 17 秒、24 个机会，JEV 约 $0.11）；预注册 12 让网络第一次在 1 万人上真跑，4 位单人冷接入第一个机会约 10.6 秒、每人 JEV $0.53–1.05、都能回到静止但要 6–12 分钟（见下面预注册表）。全量召回与难负例还没有用新召回重测。

| 项 | 数 | 说明 |
|---|---|---|
| 全量 v3（宽召回 + 重排） | 429 人接入后到 $4 上限停下；之后引擎预算耗尽、300 秒内没有静止，进程被停，评分是停下时的快照 | 与 v2 同一批 429 人比：全部召回 0.54 → 0.68，一对一/转介 t0 0.65 → 0.89（预注册 06） |
| 全量 v2 | 454 人干净接入，判过 13751 对，成立 1352 对（每人约 6 个机会），构型 1135 个，方案 212 份 | 第 454 人之后 TypeSafe 额度用完，只评之前接入的 |
| 召回（真值结构，v3） | pair+latent+relay t0 0.89、深层 0.61；团队/星/多对多 0.45；链+环 0.27；嵌套 1/3；全部 67/99 = 0.68 | v2 全部 0.50，v1 0.44 |
| 难负例 | v3：22 对里 18 对判成立，置信度区分真值对与难负例的 AUC 0.596（v2：19/23、0.636） | 精度的上限，置信度区分力弱 |
| 成立对的增长（代价） | 同一批 429 人，成立对 1253 → 1874（+50%），每人机会 5.8 → 8.7 | 召回升了，误报也多：这 1874 对的精度经盲标约 0.45（预注册 14） |
| 首个机会 | 接入后 p50 7.0 秒（v3）、3.7 秒（v2） | 重排多一次调用 |
| 花费 | v3 每人约 $0.0093（召回与重排占一半）；v2 454 人 $0.87，平均每人 $0.0019 | 跑在暖缓存上（判断缓存里已有前几轮的 54 万条，开头几人命中率 0.97），冷启动不是这个数；全量 v1 冷启动 500 人 $3.42、每人 $0.0068（旧程序） |
| 静止 | 60 人子集：接入、5 次披露、5 次离开后全部静止。一次披露重判 50–272 次调用、离开 0–12 次（sub60-v3）；另一次同规模运行是 3–80 与 0–3（abl60-base，缓存更暖） | 修前接入停止后不静止 |
| 渐进披露 | 60 人子集（sub60-v3 最终结果）339/1483 条边看到了 t1/t2（修前全量 0）；全量 v2 只有 568/23559 | 规模一大，真正走到多给一层的对很少 |

真实 agent 的五次接入见上文「一条命令接入」的表。补充两点：第一次接入里 0.73 的机会被 agent 判为误报，由此做了预注册 03/04 并改了成立规则；之后主会话把「找动效合作者」从 t1 调到 t0 重新接入，网络增量重判 64 次调用，仍没有对口的人，这 500 人的模拟世界里几乎没有 Nature 需要的人（投资人、动效作者都不在召回前 32 名里）。收件箱里会有来自判为不成立的对的请求，那是对方拿不准时来要信息，按设计会出现。五次都没有产出与真人的合作：接入链路对真实 agent 可用，价值要等真实的第二方 agent 接入后才能验证。

## 没做到与不成立的

- 10-05 最终验收反驳（Opus，[review/2026-10-05-最终验收反驳.md](review/2026-10-05-最终验收反驳.md)）判定整体没有达到目标：「只有 J++ 才能做」被本项目的基线否定（普通代码做得到，J++ 少写约三分之一；预注册 13 的差分把它测实了：补齐语义后的基线在同一条轨迹上终态全对，J++x 反而在静止前再接入时漏边）；真实使用的对方全是虚构居民，没有产生一桩与真人的合作；1 万人网络没真跑过（之后由预注册 12 跑了，见本节「规模」一条）；12 小时时限内必交项没交齐（中间断网约 6 小时，之后按 Nature 的新指示继续）。成立的有：不参考旧实现、黑板与多 agent、只交 t0 与一条命令接入、500 人时快、3D 前端、两份 Fable 裁定。它列的第二件事（真实接入者拿到方案）已由预注册 11 做到；第三件（精度与置信度的标定）已由预注册 14 测出，结果见下一条。
- 精度不到一半：离线全量 v3 判成立的 1874 对，抽 100 对盲标（Sonnet 只看判断器当时看到的材料，两遍独立标注、不一致再裁决），加权约 45% 被标为「有一件具体、双方都愿意、现在就能开始的合作」（95% 区间 0.36–0.54），11% 说不清，过半的机会经核对不成立（预注册 14）。被标「否」的多是两人不在一地而合作要当面做，或一方能给的东西对方没在找。判不成立的边少有漏网：p 低于 0.4 的 30 对里 0 对被标「是」（95% 上限约一成）。
- 置信度能排序，但只在高段有用：在判成立的边内部，p 区分盲标真假的 AUC 0.72（0.61–0.82）；分档看，p 0.50–0.65 三档都只有约三成成立，0.65–0.70 约五成半，0.70 以上约七成半。判成立的边 57% 落在 0.65 以下；公网上只交 t0 的接入者拿到的机会读数都在 0.51–0.64，若沿用这组分档，全在三成上下那一段。这组分档测自 v3（向量 + 重排召回）；公网现在是两段 JEV 召回（预注册 10）加新方案门（预注册 11），两两题没变，但进到两两判断的对不同，分档精度不一定照搬，放进界面前要在现行程序上重测。难负例仍分不开：判断器把「看起来相关、实际不成」的对大多判成立（v3 18/22），p 区分真值对与难负例的 AUC 0.596，盲标者给了 t1 也有 64% 标「是」，所以 45% 对设计好的难负例偏高。三选一的成立题能把难负例降到一半（预注册 07），但没过预先定的线，没有采用。
- 建议（没有改代码）：界面上不再把 p 当成概率直接显示。按预注册 14 的判据，数字旁写同档的实测精度，例如 0.57 写「同档实测约四分之一成立」，0.72 写「同档实测约七成半成立」，并标明是 500 人离线全量、Sonnet 盲标的数；排序仍按 p。0.65 前后分成两段（约三成、约三分之二）的说法更简单，但这条分界是看过结果后才找到的，要在另一份样本上复核后再用。这是对数字的说明，不加门槛，也不藏低分机会。
