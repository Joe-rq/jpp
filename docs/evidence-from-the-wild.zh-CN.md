# 我们把别人写的 Jev 代码读了一遍

[English](evidence-from-the-wild.md) · [为什么做 J++](why-jpp.zh-CN.md) · [现状](status.md)

在继续写 J++ 之前，我们先去看了大家实际拿 Jev 在做什么。

读的东西包括：官方文档和全部 22 篇 cookbook、两个官方 SDK、社区模式库里 35 个具名
pattern、用 SDK 依赖反查找到的约 150 个真实仓库、jevable.com 画廊的全部 194 个条目、
以及 26 篇开发者自己写的实践记录。其中 57 个生产程序按同一份模板逐行分析过。

我们本来预期会看到很多没想到的用法。这样的东西有一些，但不多。看到最多的是另一件事：
**所有人都在手写同样的几样机制，各写各的，用不同的语言，而且没有两个人写成同一个形状。**

这篇文章是那些证据，以及我们认为它对语言设计意味着什么。凡是我们自己还没做到的地方，
下面都会直说。

## 没有人缓存判断

一次 Jev 判断是材料和问题的纯函数。同样的输入给同样的答案。缓存它等于白捡钱。

57 个生产程序里，**只有一个**缓存了判断本身。另外 56 个缓存的是工具返回、本体树、
缓存键、语义指纹，就是不缓存判断。

那个做了的人写了大约 15 行：把易变字段（IP、区块 ID）正则替换成占位符，取 SHA-256，
放进一个五分钟过期的内存表。结果是 2500 次调用压到 88 次，135 万 token 砍到 4.8 万。
大约 96% 的调用根本没发生。

那另外 56 个人为什么不做？不是因为不值——上面那个数很大。是因为每个人都得从头想一遍：
哪些字段要归一化、键怎么构造、存多久。大多数人觉得这些思考不值当，而就他们个人而言
这个判断是对的。

**这正是语言该干的事。** 一次判断的身份——哪份材料、哪道题、哪条校准线——运行时本来
就知道。J++ 把它记进账本，而且我们在真机上验过重放：同一个程序对着线上模型跑三次，
账本键逐条相同。

**我们还差的部分**：账本让单个程序内的重放成立。跨程序、跨会话的那个存储设计好了
（`12` §2.10、§5），没有实现。这一条我们现在不宣称。

## 每个人都发明了自己的「我不知道」

这是唯一一个大家都会写的机制。26 个 GitHub 样本里有 18 个显式处理了低置信。

它也是唯一一个谁都不同意谁的机制：在有真实代码的样本里，**我们数出八种形状，没有两个
一样**——单阈值二分、三态区间、多信号取最小、返回一个集合而不是一个值、抛异常触发框架
降级、在候选列表里显式放一个「都不是」选项、双阈值带加全局安全阀。

阈值从 0.30 到 0.95 都有。

有一个社区 playbook 里其实写好了一个通用的路由函数：

```python
def safe_route(probability, automatic, review="human_review"):
    if probability >= 0.70: return automatic
    if probability <= 0.30: return "no_action"
    return review
```

同一个仓库里没有任何地方调用它。四个场景各写各的 if 链。

库就是这样失效的。好抽象写好了，摆在那儿，而没有任何东西逼你走它，于是每个调用点
重写一遍。

**在 J++ 里这个约束在类型系统上。** 一次判断给你的不是布尔值，是一个三态的出口，
而「拿不准」那一态是一个你**必须消费**的值：交给 handler 路由、升级、显式丢弃，
或者带进返回值交给调用者。悄悄扔掉它的程序编译不过。通配分支也兜不住它——
那一臂必须你自己写。

这部分是做好了的，从第一个内核包起就在跑。

## 生态里最常见的那行代码，正是我们禁掉的

这个形状我们在四个互不相关的项目里都看到了：

```javascript
if (result.noul("is_urgent").isYes(0.7)) { escalate(); }
```

阈值写在调用方代码里。作者们解释为什么这么写的时候，说的是同一件事：这样阈值可以
独立于模型单独调整、单独做 A/B。

**这个理由完全正确。** 一条决策边界确实应该按它自己的节奏演化，靠数据来定，
不该牵动程序逻辑。

**而把它硬编码在调用方，恰恰是保证这件事做不到的那种写法。** 源码里的一个数字，
要改就得改源码、发版本。它不是独立于代码的，**它就是代码**。

J++ 干脆不允许在程序里写线。线只能来自校准记录，而记录是在标注集上测出来的，
自带来源、样本数和证书。程序只说「把这条读数切开」，至于切在哪条线上，
不是程序该管的事。

我们知道这是我们最严的一条规则，也会是摩擦最大的一条。我们同时认为，
生态里最普遍的那个写法，是这条规则缺席时的将就办法。

**我们还差的部分**：从程序自己的运行产出一条线，这个环还没闭上。运行期的证据目前
不带真值，所以校准记录仍然要从外面给。这是我们接下来要做的。

## 平台说要批量，而工具不帮你

官方那篇 parallel questions cookbook 自己量过：把所有问题装进一次调用，
比一道一道问**便宜 12.2 倍、快 10.0 倍**。而请求格式对挂多少道题没有上限。

再看 SDK 给你什么。官方 Python SDK 的参考文档里：

```python
RetryPolicy(max_retries=2, backoff_initial=0.5, backoff_max=5.0,
            backoff_jitter=0.25, http_statuses={408, 429, *range(500, 600)},
            respect_retry_after=True, timeout=30.0)
```

这写得是真好，而它也是 SDK 唯一接管的一条缝。异步客户端的参考文档里没有并发上限、
没有信号量、没有限流。使用指南里既没有批量也没有缓存。每一次 `system_one()`
就是一个独立的 HTTP POST。

于是人们自己造，而我们看着他们造：一个项目用 `ThreadPoolExecutor(max_workers=8)`，
另一个用 `asyncio.Semaphore(16)`，第三个故意串行发批次——注释写着这是防触发限流。
三个项目各自把并发调低，理由是怕。

**在 J++ 里，同一份材料上的问题本该在构造上就合成一次调用。** 你写最自然的那种写法，
编译器把它们放进同一层。

**我们还差的部分，而且这一条挺难看的**：写这篇文章的时候我们量了自己的实现，
发现它很脆。同一份文档十四个检查点：

```
map(题组, 查)              → 1 次调用
map(题组, fn(q) { 查(q) })  → 14 次调用
```

结果完全一样，零警告。差别只是一次 eta 展开——把函数包进一个立刻调用它的 lambda，
这个变换在任何函数式语言里都是恒等的。

原因是结构性的，而这才是这个发现有用的地方。我们的内核设计说，过滤算子吃的是
**一组材料和一道题**。我们的实现把它做成了吃**一个列表和一个闭包**，一个名字相同的
普通列表操作。一旦有闭包，就有东西可以往外包一层，融合那个 pass 就认不出形状了。
换成设计里那个算子，根本没有闭包可包，融合也不再是一个 pass——**它就是这个算子的含义**。

我们要改的是算子，不是那个 pass。

## 四个程序会循环，四个都用三道刹车

多轮程序很少见——Jev 本身是一次判断，所以大多数用法是单轮。我们找到四个真的：
一个宝可梦对战 agent、一个 computer-use agent、一个端到端测试驱动，
一个逐小节生成音乐的程序。

四个都用三条彼此独立的终止条件：硬步数上限、无进展检测、模型自己认为做完了。
**没有一个让模型的判断单独终止循环。**

这是个好直觉，而且四个人分别有了这个直觉。步数上限管得住失控的循环，
管不住一个每步都合法却在原地绕圈的程序；无进展检测管得住绕圈，
管不住一个觉得自己还没做完的模型。而判断本身可能自信地错，所以它不能是唯一的刹车。

四个里最干净的那个值得描述一下。外层一个 `while (!battle.ended)` 驱动一个确定性的
对战引擎。每一回合，把结构化状态——HP、属性、技能、天气——渲染成题面，
一次选择题挑一个技能，引擎执行并推进。终止来自引擎判定胜负和一个硬决策上限。
作者在 README 里写明，他们没有对低置信度的答案做脚本化替换。

**我们认为这就是对的架构**：确定性引擎驱动世界，判断负责每一步选一个动作。

**我们还差的部分**：我们的有界循环只吃一个整数上界。无进展那条线做了一半，
而且没有表面语法。完成判断根本驱动不了它，因为打分题的档位没有接到循环进度上。
三道刹车我们有一道。

## 没有人做二阶，而这恰恰是有意思的地方

我们专门找了「用 Jev 的输出决定下一轮问 Jev 什么」的程序。

26 篇社区实践记录里，**一个都没有**。

官方旗舰 cookbook 最接近，值得说准确一点：每一轮由**另一个通用推理模型**提出新问题，
Jev 在各行数据上作答，一个梯度提升模型重新拟合，代码保留那些降低了交叉验证误差的问题。
轮数硬编码为五，文档自己写明没有做自适应终止。所以决定问什么的是一个贵的文本模型，
Jev 是执行层。

有两篇官方 cookbook 确实用上一轮的结果构造下一轮，而且两篇都是**确定性地**构造。
一个技能路由器把 182 个候选排序，取前三切片，直接从这个切片构造第二轮的选项集合和
逐候选的问题——而且第二轮还能把这三个全部否掉。另一篇函数调用的 cookbook 读函数的
类型签名，每条命令自动生成 54 道题，整个过程里没有模型。

我们认为确定性那条路更好，而且几乎没人探过。它更便宜、可复现，而且它需要的那个结构
——**问题是一个可以构造、可以检视、可以传递的值**——是语言给得了而 SDK 给不了的。

这是 J++ 还没做的部分。在我们的实现里问题还不是一等值，你甚至读不回一道题的题面。
这是我们的设计和代码之间最大的一个差距，而做完这次调研之后，
它也是我们最确信值得补上的一个。

## 我们没覆盖到的

诚实交代边界，因为上面的数字只和样本一样可靠。

jevable 画廊列了 194 个项目，我们枚举到 177 个，确认源码的有 20 个仓库。
画廊条目链到 X 帖子，我们抓不动——页面是客户端渲染，没有可用的元数据——
所以找源码主要靠在 GitHub 上按项目名和作者反查，而只要某人的 GitHub 登录名和社交
handle 不一样，这条路就断。我们这样确认的四个仓库里有三个是靠真实姓名找到的，
不是靠 handle。

最弱的一块是游戏：画廊里 39 个，确认源码的只有一个。游戏正是多轮深度最密集的地方，
所以上面那一节的证据只建立在四个程序上，其中只有一个是游戏。
**这是「我们没找到」，不是「它不存在」。**

我们也没有扫那 50 个开发者工具条目。当连续三批采样都只在确认已有结论、
没有改变任何一条时，我们停了。

## 简短版

九样机制被反复手写：判断力缺席时的降级（五种语言里七份独立实现）、
确定性预筛让模型只做窄判断（八份以上）、多信号合成取最坏而不取平均（六份）、
用三到四态的结果枚举代替 try/catch（四份）、三道刹车的终止（四份）、
对调过的题面做 fit 加 holdout 验收（两份独立重新发明了同一套流程）、
重试逻辑（Rust 和 JavaScript 两份结构几乎相同）、beam 式路径搜索（两份）、
以及工具路由场景普遍收敛的「先选后填」两步调用。

把这九样放回我们的内核——两个类型、一座桥、一道题、三值、五个算子、一本账——
**其中七样在设计里早就有位置。** 人们在手写的东西，我们的设计已经考虑到了，
是我们的实现没跟上。

只有一样完全没有位置：**当判断能力本身不在的时候，程序该怎么办。**
七个人用五种语言发明了同一个答案，而我们连这个问题都没提过。

这是这次调研给我们最有用的东西，也是我们为什么要在写更多代码之前先做它。
