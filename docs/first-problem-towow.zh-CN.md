# 第一个应用问题：能不能让计算不断产生新的合作可能？

2026-09-20 · Nature 提出的构想，随 J++ 开源讨论。本文提出研究方向；[十人案例](towow-demo.zh-CN.md)是这个方向的第一个可运行切片。

J++ 想成为一种通用的编程语言：少量基本操作能组合成方法，方法能继续组合，组合的产物又能进入新的计算。通爻的网络发现问题，让这个抽象有了一个具体的去处。

**是不是可以让一个主体发出的模糊意图，在遇到不同主体的本地上下文时，产生他自己没有想到的合作可能？是不是可以让这些正在形成的可能性，立即成为下一轮计算和传播的材料？**

## 问题从哪里来

设想一个有一亿个主体的网络。主体彼此陌生，持续加入、离开，各自有丰富且不断变化的本地上下文。没有谁掌握全网的信息，也没有一种预先设计的需求表能描述所有人可能创造的价值。

一个人只说：“最近创业很累，不想再讲道理了。”他还没有提出一个精确需求，更不知道应该找谁。

这句话遇到心理咨询师的上下文，可能出现一次支持性交流的候选。遇到一位奶奶的上下文，会得到另一种可能：“我儿子开车时很会让人放松。”再结合儿子的经历，发现他曾陪过处境相似的创业者。三方的信息合在一起，出现了“有人陪伴的轻松出行”这一候选。

这个候选再遇到投资人的上下文，可能引出一个值得调查的服务方向；遇到其他创业者，可能出现新的需求和参与条件。最初的人没有输入这些检索词，也没有预先写下这份合作方案。

通爻此前的发现层研究把问题写得很明确：发送者无法点名对方；关系的价值在接收方的本地世界中产生；输出应包含候选组合与触发原因，支持直接关系、中继关系和多方组合。发现层尽量保留可能性，更深入的交互再细化方案。候选是给人启发的材料，实际合作仍需要参与者回应。

## 这次直觉里最重要的一步

**进行中的计算，也可以参与其他计算。**

主体的可发现表示，可以来自当前语料、其他主体的中间结果、正在变化的关系读数，以及尚未完成的合作构型。一个主体自己的文字没有变化，他与其他人的潜在关系也可能因为这些计算而变化。

例如，司机的背景没有变，但他目前可参与的时间改变了；某个候选小组形成了；另外两个主体正在调查的需求方向发生了变化。这些局部结果可以让投资人、组织者或新的参与者重新发现他，而不必等整个任务“完成”后再统一更新画像。

这里的读数必须带着它回答的问题、材料版本和参照含义。“值得继续了解”和“已经愿意参加”表达的是不同关系，不能相加成一个看似通用的数字。画像也可以有多个侧面，不必只是一条静态向量或一个总分。

可以把这条构想写成一个循环：

```text
模糊意图 × 接收方当前上下文
    → 一种关系判断 / 新问题 / 候选构型
    → 与其他主体、构型和进行中的计算继续组合
    → 更新可发现表示与下一步传播方向
    → 进入更多局部计算
```

## 为什么想到用一门语言来表达它

直接调用 JEV，可以完成一次结构化判断。我们想用 J++ 编写整个计算方法：如何构造问题、准备材料、保留未知、展开转介、组合多个主体，以及如何把这些方法再交给其他方法使用。

如果组件接口能够容纳这些结果，运行系统就有机会把通用算法的力量带进来：独立判断并发执行，同一计算被不同上层方法共享，未变化的输入复用已有结果，新材料只触发依赖它的部分，反馈继续构造下一道问题。具体采用哪些算法，应由程序和运行条件决定。

这会产生一个值得探索的效果：一个复杂的合作发现方法，封装后仍是一段别人可以调用、替换或组合的方法。十个人的候选组合也可以成为更大计算的输入。开发者不必为每个场景重新搭建一次模型调用、缓存和传播流程。

JEV 是启发这个项目的一类语义判断能力；精确计算、检索、生成、异步执行和分布式算法可以共同参与。J++ 应允许后端升级或替换。通爻是应用问题之一，不限定语言只能实现网络发现。

## 能否进一步走向大网络？

是不是可以让持续计算维护的局部线索，帮助网络决定“下一次值得和谁深入计算”，从而减少每次对全网重新比较的需求？是不是可以把已有公共参照（例如通爻研究中的 NAC）与可编程的端侧算子、组合结果和更新策略结合？是不是可以让成功发现的中间结构，成为下一次发现可复用的工作？

这些问题保留原有难度：投影会丢失信息，主体各自拥有不同上下文，全局信息不完整，新的关系会在互动中生成。探索路径也需要为当前表示尚未覆盖的可能性留位置。分布式执行和隐私保护可进一步研究；节点分散本身不等于加密。

亿级是我们希望研究的目标尺度。十人程序首先展示局部计算怎样组成发现过程，它不承担亿级性能的结论。

## 第一个可运行切片

先用十个虚构主体，其中一人发出模糊意图，其他主体提供各自的上下文。程序应展示：

1. 同一个意图怎样在不同接收方产生不同候选，包括直接支持和转介。
2. 转介取得的新材料怎样进入计算，多方候选怎样继续成为其他主体的输入。
3. 一次局部变化怎样更新关系；未变化的判断如何复用。
4. 哪些工作由现有 J++ 的问题值、组件组合、批量判断和运行记录承担，哪些是案例自己的发现策略。

运行结果需标明真实模型、录制回放和合成测试的区别，分别记录实际耗时、请求数量和复用情况。速度需要与同一输入、同一问题集合的执行方式比较，不能把缓存回放时间写成模型推理时间。

这次切片先使用有限轮次的候选传播。任意进行中计算的订阅、自动增量依赖以及真正分布式的持续网络，是它希望推动的后续语言能力。

## 邀请共同构造

我们想公开的是一个可继续发展的想法：**能不能把“计算产生关系，关系参与计算”写成普通开发者能够组合的程序？**

欢迎提交自己的主体上下文、发现方法或替代算法，也欢迎展示现有接口在哪里无法表达你想要的组合。最有帮助的贡献，是一个别人能运行、修改并继续组合的例子。

本文由 Nature 的连续讨论整理，并回读了通爻发现层规格的目标、端侧算子、传播与候选组合定义，以及发现引擎关于方案启发和参与者选择的定义。上述情境是合成示例，不包含真实个人的语料；没有公开内部研究档案或把其中历史实验当作本案例结果。
