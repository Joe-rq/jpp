拦住 113 / 126 = 89.7%；拦住的报文全部带「修法」。**修后（`ir-impl-2` 修 D1，2026-09-21）：126 / 126 = 100%**——检查器把 `for e in R` / `zip(…, R)` / `enumerate(R)` / 生成式解包出的元素名记为读数变量，`match` 与 `isinstance` 位置的读数（含 `R[0]` 下标）都报 J-01 带修法；运行期 `Exit` 的 `__instancecheck__` 收到读数直接抛 J-01，`match e: case jv.Act()` 第一个 case 就报错而不再静默不命中（`tests/test_jv_passes.py::test_d1_*`）。

**漏网的 13 个全在模式 1，同一形态**：程序把向量化读数赋给变量，再经 `zip`/`for` 解包后对元素 `match`：

```python
exits = jv.judge([jv.state(on=w, over=部门集) for w in 工单流], 该部门)   # 忘了 jv.cut
for w, e in zip(工单流, exits):
    match e:
        case jv.Pick(k): ...
```
检查器只追「直接绑定 judge 的名字」和「match 直接作用在 jv.judge(...) 上」，追不到 `e`。更严重的是**运行期也静默**：`e` 是 `Readings`，`case jv.Pick(k)` 不命中，`out` 为空，没有出口登记，J-05 无从报错——`工单路由` 变体返回 `{}`，`提交信息一致` 变体返回 `{'未见': [], 'unsure': []}`，都不报错。13 条程序里凡是向量化写法的都中。这是本次最重要的发现，修法见 §5-1。

模式 1 在 8 条程序里拦住，都是 `match jv.cut(jv.judge(…)[0])` 直接内联的写法（去掉 cut 后 match 的对象仍是 `jv.judge(...)` 调用）。

## 4. 21 条程序里发现的实现摩擦（不是缺陷，但影响写法）

- `jv.transform(f, *args)` 的参数只能是 `Mat`、期物或纯 JSON 值；`transform` 返回的**列表**不能整体再传给下一个 `transform`（`canon` 序列化 `Mat` 列表报 TypeError），必须 `*xs` 摊开并另传长度（`入侵迹象` 的 `pairs_with(n, *items)`）。
- `isinstance(x, jv.Mat)` 对 `do` 的期物为假。用它判断「是不是材料」再取 `.content` 的辅助函数会静默把期物当普通值（`生成到全绿` 的变式函数因此一度读到 0，循环一轮就停）。正确写法是直接读 `.content`（刷新点）。
- 文法的 `escalate 疑`（把一批拿不准交给人）在构建器里是两步：`jv.consume(exits, unsure=jv.drop)` 消费出口，再 `jv.escalate(疑)` 记账；`jv.consume(exits, unsure=jv.escalate)` 会逐个 `ask` 并 `Pending`，语义不同。
- 文法的 `mark_unsure(疑)` 没有对应物；返回值里带 unsure 分量要自己收集（`jv.handle(c, keep=None)` 或按 `isinstance(e, jv.Unsure)` 过滤）。
- 一道 select 的候选落在档案未测档（120–250 token）时每条含 select 的程序都收到两条 `W-untested`（K-noul 保守 + 置换同调用串扰未测），噪声大但按 J-15 是对的。

## 6. 包缺陷（不修，给 `ir-impl-2`；最小复现）

> 处置（`ir-impl-2`，2026-09-21）：D1 修（运行期 J-01 + 静态解包追踪，拦截率 113 → 126 / 126）；D2 修（`transform`/`do` 参数含材料列表时键按元素哈希递归，`_arg_hash`）；D3 修（`plan` 对「循环里 cut 循环外登记的向量」按登记处倍率算层，`找矛盾论文对` 类写法报 1 层）；D4 不是缺陷。另：`six.py` 的 `定位回归` off-by-one 改 `(len-1)//2`（规范原文不动，README §4）；`jv.loop` 无进展 / 键重复停止改为显式记 `Unsure(noprogress)` + `W-noprogress`（循环即 handler，置 consumed）。`twentyone.py` 里的 `定位回归` 副本仍是规范原文 `len//2`，未动（属 programs-21 的文件）。

- **D1 读数向量元素 `match` 静默不命中（运行期）**：
  ```python
  with jv.Runtime(client=jv.FakeClient()) as rt:
      rt.calib.put("k", hi=.6, lo=.3, n=50, status="上岗")
      @jv.program(check_static=False)
      def f():
          v = jv.judge([jv.state(on=jv.lit("a"))], jv.test("q", calib=jv.calib("k")))
          out = []
          for e in v:
              match e:
                  case jv.Act(): out.append(1)
          return out
      f()   # → []，无异常，exits=0
  ```
  期望：`isinstance(Readings, jv.Act)` 抛 J-01。
- **D2 `transform` 不收材料列表**：`jv.transform(lambda xs: len(xs), jv.transform(lambda m: ["a", "b"], jv.lit("x")))` → `TypeError: Object of type Mat is not JSON serializable`（`canon` 在算键时）。期望：报 J-11 风格的清晰错误，或接受列表。
- **D3 `plan` pass 对「循环里 cut 已登记向量」高估层数**：`找矛盾论文对` 报 `W-cost: 层数上界 |ps| 含符号，budget.layers=1`，实测 1 层。估计器把循环体内的每个 `cut` 当成一层，没看它 cut 的是循环外登记的向量元素。
- **D4 并行改包期间的一次瞬态**：本步跑到一半 `runtime.py` 出现 `NameError: _Frame`（`ir-impl-2` 改到一半），几分钟后恢复；不是交付物缺陷，记一笔说明本次数据是在包稳定后重跑得到的（169 passed）。

## 7. 最薄弱处

静态检查器追踪读数变量的方式是「名字直接绑定 judge」，一经解包就丢；而运行期把「读数当出口」当成普通的不命中而不是类型错。两层都放过同一种误写，且这种误写恰恰出现在融合率最好的写法（向量化）里——鼓励的写法和最容易静默出错的写法是同一种。§5-1 的两处修法都很小（检查器多追一类绑定；`__instancecheck__` 多一个 raise），但在修之前，自举（生成器写程序 → 检查器指错）对模式 1 的拦截率只有 8 / 21。
